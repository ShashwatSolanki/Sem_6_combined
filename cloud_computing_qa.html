Cloud Programming Models

Q1
Explain the following terms with respect to Cloud Computing: (a) Elasticity, (b) Rapid Provisioning, (c) Measured Service, (d) Resource Pooling
Most AskedUnit 1
▼

a) Elasticity

Elasticity is the ability of a cloud platform to rapidly increase or decrease computing resources to cope with changing loads dynamically. It refers to the actual scaling action—adding or removing resources in response to demand. For example, a web application may need more servers during peak traffic and fewer during off-peak hours.

Key distinction: Elasticity is dynamic (real-time), whereas Scalability is the potential/capability to grow. Elasticity is about doing, scalability is about being able to do.
  • Scale Up (Vertical Scaling): Adding more power (CPU, RAM) to existing servers.
  • Scale Out (Horizontal Scaling): Adding more servers to distribute load.
  • Scale Down: Releasing unused resources to save cost.

b) Rapid Provisioning

Rapid provisioning means that cloud resources (compute, storage, networking) can be acquired and released quickly—within minutes—with minimal management effort or service provider interaction. This is also called "on-demand self-service." Users can self-provision resources through a web portal or API without calling a helpdesk.

c) Measured Service

Cloud systems automatically control and optimize resource use by leveraging a metering capability. Resources usage is monitored, controlled, and reported transparently. This enables the "pay-as-you-go" or "pay-per-use" business model—consumers pay only for what they actually consume. Examples: AWS billing by GB-hour of storage, per-second compute billing.

d) Resource Pooling

The provider's computing resources are pooled to serve multiple consumers using a multi-tenant model. Physical and virtual resources are dynamically assigned and reassigned according to consumer demand. Customers generally have no control or knowledge over the exact physical location of provided resources (location independence). Example: Multiple customers share the same physical servers through virtualization.

Q2
List and explain the benefits of moving applications to the cloud.
Most AskedUnit 1
▼
  • Scalability: Applications on the cloud have a better ability to scale up or down based on IT requirements and business plans. Resources can be added or removed as demand changes.
  • Cost Reduction: Organizations can reduce operational costs while improving IT processes. Applications pay only for what they use, eliminating the need to maintain costly data centers. Capital expenses (CapEx) are replaced with variable operational expenses (OpEx).
  • Integration: Cloud allows businesses to seamlessly connect systems together and improve efficiency with all services, alleviating risks like hardware refresh cycles.
  • Accessibility: All data is stored in the cloud so it can be accessed from anywhere regardless of what happens to physical machinery. Applications are available from desktops, laptops, and mobile devices.

  • Elasticity: Scale resources up or down instantly as business needs change—ideal for handling peak loads without over-provisioning.
  • Deployment Speed: Cloud enables global expansion and deployment in minutes rather than weeks or months.
  • Disaster Recovery: Cloud platforms provide built-in backup, redundancy, and disaster recovery options.

Q5
Explain different degrees of parallelism with an example.
Most AskedUnit 1
▼

Parallelism refers to executing multiple computations simultaneously. There are several degrees:

Bit-Level Parallelism

Increases the processor word size, allowing more data to be processed per operation. Example: Moving from an 8-bit to a 32-bit processor means a 32-bit addition can be done in one clock cycle instead of four. Modern 64-bit CPUs process 64 bits at a time.

Instruction-Level Parallelism (ILP)

Multiple instructions are executed simultaneously within the same processor. Techniques include pipelining (overlapping execution stages of multiple instructions) and superscalar execution (dispatching multiple instructions per clock cycle). Example: A CPU pipeline processes Fetch, Decode, Execute, Writeback stages for different instructions simultaneously.

Task-Level Parallelism

Different tasks or processes run simultaneously on multiple processors/cores. Example: In a web server, each HTTP request is handled by a separate thread/process running in parallel. In MapReduce on Hadoop, the Map phase processes multiple data partitions on different nodes simultaneously.

Data Parallelism

The same operation is applied to multiple data elements simultaneously. Example: GPU computing applies the same shader operation to thousands of pixels in parallel.

Q6
What are the differences between monolithic and microservices applications? What are the challenges associated with migrating monolithic applications?
Most AskedUnit 1
▼

Monolithic Architecture

A monolithic application is built as a single, indivisible unit. All components (UI, business logic, data access) are tightly coupled and deployed together.

Advantages: Simple to develop initially, easy to deploy (copy one artifact), simple scalability (replicate the whole app).

Disadvantages: As the app grows, the codebase becomes complex; hard to scale individual components; a failure in any part can bring down the whole app; technology stack is locked in.

Microservices Architecture

Microservices are small, independent services that each handle a specific business capability, communicate over APIs (usually REST/HTTP or messaging queues), and can be deployed independently.

Advantages: Independent scalability, independent deployment, different services can use different technologies, failure isolation, easier for large teams.

Disadvantages: Higher complexity in inter-service communication, distributed tracing, service discovery, and data consistency.

Key Differences

AspectMonolithicMicroservices
DeploymentSingle deployable unitEach service deployed independently
ScalabilityScale the whole appScale individual services
TechnologyOne tech stackPolyglot (different tech per service)
FailureOne failure can crash allFailures are isolated
CommunicationIn-process function callsNetwork calls (REST/messaging)

Challenges of Migrating Monolithic Applications

  • Identifying boundaries: Decomposing a tightly coupled monolith into independently deployable services is difficult—domain boundaries are unclear.
  • Data management: The monolith often has a single shared database. Splitting it per-service requires complex data migration and handling distributed transactions.
  • Distributed transactions: ACID transactions across multiple services are complex—handled with the Saga pattern (chain of local transactions with compensating transactions on failure).
  • Testing complexity: Integration testing across many independent services is harder.
  • Operational overhead: Requires container orchestration, service discovery, load balancing, distributed logging and tracing.
Q7
Explain the four core concepts of the publisher/subscriber model used in asynchronous communication. What are the different purposes for which the pub/sub model can be used?
Unit 1
▼

Four Core Concepts of Pub/Sub

  1. Message: The data payload that is published. It contains the event or information that needs to be communicated.
  2. Topic: A named channel/subject to which messages are published. Publishers send messages to topics; subscribers express interest in topics.
  3. Publisher (Producer): An entity that creates and sends messages to a topic. Publishers are decoupled from subscribers—they don't know who receives the messages.
  4. Subscriber (Consumer): An entity that registers interest in a topic and receives messages published to that topic. Multiple subscribers can receive the same message (fan-out).

How It Works

When a publisher sends a message to a topic, all subscribers of that topic immediately receive it. The publisher and subscriber are temporally and spatially decoupled—publishers don't need to know if subscribers are running, and subscribers receive messages even if the publisher has stopped.

Purposes of Pub/Sub

  • Event notification: Notifying multiple services when an event occurs (e.g., order placed → notify billing, inventory, shipping services).
  • Multiple subscribers: Fan-out to multiple consumers simultaneously.
  • Decoupling services: Services don't need direct knowledge of each other; improves resilience.
  • Stream processing: Real-time data pipelines (Apache Kafka).
  • Log aggregation: Collecting logs from multiple services to a single subscriber.

Explain REST operations and the REST architectural style with its four principles.
Most AskedUnit 1
▼

REST (Representational State Transfer)

REST is an architectural style for designing networked applications. It uses HTTP protocol and treats everything as a resource accessed via URIs. REST is the foundation for microservices communication.

Four Key REST Principles

  1. Client-Server: Clear separation between UI/client and data storage/server. This improves portability of the UI and scalability of the server components.
  2. Stateless: Each request from client to server must contain all information needed to understand and process the request. No session state is stored on the server between requests. Each request is independent.
  3. Uniform Interface: A consistent, standardized interface between components. Resources are identified by URIs; interactions happen through a fixed set of operations.
  4. Layered System: Client cannot tell whether it is connected directly to the end server or to an intermediary (proxy, load balancer, etc.). Enables scalability through caching, load balancing.

Q9
What is serverless computing? List the advantages. Give an example real-world cloud service that employs serverless computing.
Unit 1
▼

Serverless computing is a cloud execution model where the cloud provider dynamically manages the allocation and provisioning of servers. Developers write and deploy code (functions) without managing underlying servers. The provider automatically scales the infrastructure.

Advantages

  • No server management: No need to provision, patch, or manage servers.
  • Pay-per-execution: Charged only when code runs, not for idle time.
  • Automatic scaling: Scales automatically from zero to peak demand.
  • Faster development: Developers focus only on business logic.
  • High availability: Provider handles fault tolerance and redundancy.

Example: AWS Lambda—execute functions in response to events (HTTP requests, S3 uploads, DynamoDB changes) without managing servers. Also: Azure Functions, Google Cloud Functions.

Serverless is ideal for event-driven, stateless, short-duration workloads such as image processing, notification sending, and API backends.

Discuss the most common technology challenges that occur in cloud computing.
NewUnit 1
▼
  • Scalability: Cloud applications must handle growth in users, data, and requests. Scaling may be vertical or horizontal, but the design must avoid bottlenecks.
  • Elasticity: Resources should expand and shrink with demand. The challenge is to automate this without over-provisioning or affecting response time.
  • Performance unpredictability: Shared infrastructure, virtualization overhead, noisy neighbours, and network variability can make performance less predictable.
  • Reliability and availability: Cloud systems run on large distributed infrastructure where machines, networks, and software can fail. Replication, failure detection, checkpointing, and recovery are needed.
  • Security: Data and computation run on shared infrastructure, so access control, isolation, encryption, monitoring, and secure APIs are essential.
  • Compliance: Applications may need to satisfy legal, privacy, audit, or data-location rules.
  • Multi-tenancy: Multiple customers share pooled resources, so the system must maintain isolation while still achieving high utilization.
  • Portability and migration: Existing applications may need design/code changes before they work correctly in cloud environments.
Q11
Explain cloud architecture and key design considerations for building a cloud-ready application.
NewUnit 1
▼

Cloud architecture describes the technology components of a cloud system and the relationships between them. The front end is the client side through which users access services; the back end is the provider side that hosts applications, services, storage, runtime platforms, management, and security.

Main Components

  • Client infrastructure: browser, mobile app, API client, or portal used by consumers.
  • Application/service layer: SaaS applications, microservices, or APIs exposed to users.
  • Runtime/platform layer: PaaS middleware, databases, queues, web servers, and development/runtime support.
  • Infrastructure layer: virtual machines, containers, networks, load balancers, and storage.
  • Management and security: monitoring, provisioning, scheduling, access control, billing, and policy enforcement.
Diagram idea: Client/Front End → Internet/API Gateway → Cloud Services/Application Layer → Platform/Runtime → Virtualized Compute + Storage + Network, with management and security spanning all layers.

Cloud-ready Design Considerations

  • Design for horizontal scaling and stateless service instances wherever possible.
  • Use loose coupling through REST APIs, message queues, or pub/sub communication.
  • Plan for failures using redundancy, retries, checkpointing, recovery, and failover.
  • Separate data from compute so that instances can be replaced without losing state.
  • Use security by design: authentication, authorization, isolation, encryption, and audit logging.
  • Keep observability in mind: logs, metrics, alerts, and health checks.

Q13
Explain distributed system models with an example.
NewUnit 1
▼

A distributed system is a collection of independent computers that appear to users as a single coherent system. The slides classify common structures into models such as client-server, peer-to-peer, and layered/multi-tier systems.

  • Client-server: Clients send requests to servers that provide services. Example: a browser requesting pages from a web server.
  • Peer-to-peer: Nodes act as both clients and servers. Work and data can be spread across peers, reducing dependence on a central server.
  • Three-tier/layered model: Presentation, application logic, and data are separated. Example: web UI → application server/API → database/storage.
  • Message-queue/pub-sub model: Components communicate asynchronously through queues or topics. This improves loose coupling and resilience.
Cloud applications often combine these models: a client-server API, microservices behind it, queues for asynchronous tasks, and distributed storage for persistent data.

What is the difference between a hosted hypervisor (Type 2) and a bare metal hypervisor (Type 1)? Give an example of each. Most Asked
Most AskedUnit 2

Type 1 — Bare Metal Hypervisor

A Type 1 hypervisor (also called VMM—Virtual Machine Monitor) runs directly on the physical hardware without an underlying host OS. It directly controls the hardware and manages guest VMs. It provides the best performance and is used in enterprise and cloud environments.

Examples: VMware ESXi, Xen, Microsoft Hyper-V, IBM CP/CMS, KVM (debated—it's integrated into Linux kernel).

Type 2 — Hosted Hypervisor

A Type 2 hypervisor runs as an application on top of a host operating system. The host OS manages hardware resources and the hypervisor runs as software on top of it. Easier to set up but introduces additional overhead from the host OS layer. Commonly used for development and testing.

Examples: VMware Workstation, Oracle VirtualBox, QEMU.

Q15
How are paravirtualization and full virtualization techniques used to virtualize x86?
Most AskedUnit 2
▼

Background: The x86 Virtualization Problem

x86 has 4 privilege rings (Ring 0–3). In normal operation, the OS runs at Ring 0 (most privileged) and applications at Ring 3. Some x86 instructions behave differently at Ring 0 vs Ring 1—they are "non-virtualizable" (they don't trap when executed in unprivileged mode but silently fail). This makes simple trap-and-emulate impossible on x86 without modifications.

Full (Transparent) Virtualization

The guest OS runs without any modification. The hypervisor uses binary translation at runtime to intercept and emulate privileged and sensitive instructions.

  • At runtime, the VMM scans guest OS kernel code and replaces non-virtualizable instructions with traps into the VMM.
  • Safe instructions run directly on the hardware (for performance).
  • Guest OS is unaware it is being virtualized.
  • Example: VMware Workstation, Oracle VirtualBox.

Paravirtualization

The guest OS kernel is modified at compile time to replace all privileged/sensitive instructions with explicit hypercalls to the hypervisor.

  • Guest OS is aware it is being virtualized—it cooperates with the hypervisor.
  • Performance is better than full virtualization because no binary translation overhead at runtime.
  • Requires source code of the guest OS to be modifiable (works with Linux, not with proprietary OS like Windows without patches).
  • Guest OS typically runs at Ring 1 instead of Ring 0.
  • Example: Xen hypervisor.
Key difference: Full virtualization modifies at runtime (binary translation); Paravirtualization modifies at compile time (hypercalls replace privileged instructions).

Q18
What is the difference between hot migration and cold migration? Explain pre-copy and post-copy techniques of hot migration.
Most AskedUnit 2
▼

Cold Migration

The VM is shut down (powered off) before migration. The disk image and configuration are transferred to the destination host, then the VM is restarted there. This results in downtime but is simpler and guarantees a clean, consistent state.

Hot (Live) Migration

The VM is migrated while still running, with minimal or zero downtime. The VM continues serving requests during the migration process. Used in production environments for load balancing, hardware maintenance, and failover.

Pre-Copy Technique

The dominant approach for live migration:

  1. Iterative rounds: Memory pages are copied to the destination while the VM is still running on the source.
  2. Dirty page tracking: Pages modified during copying (dirty pages) are re-copied in subsequent rounds.
  3. Stop-and-copy: When dirty pages become small enough (convergence), the VM is briefly suspended, remaining dirty pages are copied, and the VM is resumed on the destination.
  4. Advantage: Very short stop time. Disadvantage: Memory-intensive workloads with high write rates may not converge easily (too many dirty pages).

Post-Copy Technique

  1. VM is immediately suspended and its CPU state and minimal memory are transferred to the destination.
  2. The VM starts running on the destination immediately.
  3. When pages not yet transferred are accessed, a page fault occurs—the destination requests the missing page from the source on demand.
  4. Advantage: Only one copy of each page is needed (no re-copying dirty pages). Disadvantage: If the source fails before all pages are transferred, the VM is lost; network latency for page faults impacts performance.
Q19
Explain Docker architecture with a neat diagram description.
Most AskedUnit 2
▼

Docker uses a client-server architecture with three main components:

1. Docker Client

The primary interface for users. Commands like docker run, docker build, docker pull are typed by the user. The client sends these commands to the Docker Daemon via REST API over UNIX sockets or a network interface. The client can communicate with more than one daemon.

2. Docker Daemon (dockerd)

Runs on the Docker Host. Listens for Docker API requests and manages Docker objects: images, containers, networks, and volumes. A daemon can also communicate with other daemons to manage Docker services (Swarm).

3. Docker Registry

Stores Docker images. Docker Hub is a public registry. Private registries can be hosted within an organization. When you run docker pull, images are downloaded from the registry; docker push uploads images.

Docker Objects

  • Images: Read-only templates used to create containers, built from Dockerfiles. Each instruction in a Dockerfile creates a layer (enabling incremental rebuilds).
  • Containers: Running instances of images. They add a writable layer on top of the read-only image layers (using UnionFS like overlay2/AUFS).
  • Volumes: Persistent storage that outlives container lifecycle.
  • Networks: Enable communication between containers.

UnionFS (Union File System)

Docker uses UnionFS to stack multiple read-only image layers with one writable container layer. This allows multiple containers to share base image layers (saving disk space) while each has its own isolated writable layer.

Q20
Explain Kubernetes architecture with a neat diagram showing all key components of master and worker nodes. What are controller-manager, kubelets, and pods?
Most AskedUnit 2
▼

A Kubernetes (K8s) cluster consists of a Master node (control plane) and multiple Worker nodes.

Master Node Components

  • kube-apiserver: Exposes the Kubernetes API. Entry point for all REST commands to control the cluster. All admin operations go through here.
  • etcd: Distributed key-value store that stores all cluster data (configuration, state, secrets). Used for shared configuration and service discovery.
  • kube-scheduler: Watches for newly created Pods with no assigned node and selects a node for them to run on, based on resource availability and constraints.
  • kube-controller-manager: Runs controllers that watch the cluster state via the API server and make corrective changes. Examples:
    • Replication Controller: Ensures the correct number of pod replicas.
    • Node Controller: Manages node lifecycle.

Worker Node Components

  • Kubelet: An agent running on each worker node. Gets pod configurations from the API server and ensures described containers are running and healthy.
  • kube-proxy: Network proxy running on each node. Handles network routing for TCP/UDP packets; implements load balancing for services.
  • Container Runtime: Software responsible for running containers (Docker, containerd, CRI-O).

Pods

The smallest deployable unit in Kubernetes. A Pod contains one or more containers that share the same network namespace (same IP address) and storage volumes. Containers in a Pod are co-scheduled on the same node.

Service

A logical collection of Pods. Provides a stable IP/DNS name and load balancing for accessing the pods, even as they are created/destroyed dynamically.

Q21
Explain Shadow Page Tables with a neat diagram. What are the challenges? How do Nested/Extended Page Tables overcome the software overheads of shadow paging?
Unit 2
▼

Memory Virtualization Challenge

In a virtual machine, the Guest OS manages its own page tables mapping Guest Virtual Addresses (GVA) → Guest Physical Addresses (GPA). However, GPA is not the real physical address—the VMM manages the mapping GPA → Machine Physical Addresses (MPA). The CPU's MMU uses the page table to translate addresses but only understands one level of mapping.

Shadow Page Tables

The VMM maintains a shadow page table that directly maps GVA → MPA, combining both translations. The VMM keeps the shadow page table in sync with the guest page table.

  • When the guest OS modifies its page table, the VMM traps the write and updates the shadow page table accordingly.
  • The hardware MMU uses the shadow page table directly.

Challenges of Shadow Page Tables

  • Overhead: Every guest page table modification causes a trap to the VMM, leading to high overhead.
  • Memory overhead: A separate shadow page table must be maintained for each guest process on each VM.
  • TLB flushes: Context switches between VMs require TLB invalidation, causing performance loss.
  • Synchronization complexity: Keeping the shadow page table consistent with the guest table is complex.

Nested/Extended Page Tables (Hardware Solution)

Modern CPUs (AMD-V's NPT, Intel's EPT) provide hardware support for two-level page table walking:

  • The hardware MMU walks the Guest Page Table (GVA → GPA) and then automatically walks the Host Page Table (GPA → MPA) using hardware.
  • No VMM trapping on every guest page table modification needed.
  • Reduces hypervisor overhead significantly; no software shadow page tables needed.
  • Improves VM performance dramatically for memory-intensive workloads.

Q23
Explain privilege rings in x86 and the instruction execution problem in virtualization.
NewUnit 2
▼

x86 processors provide privilege rings. Ring 0 has the highest privilege and is normally used by the operating system kernel. Ring 3 has the least privilege and is used by user applications. Rings 1 and 2 exist but are rarely used by ordinary operating systems.

  • Privileged instructions should execute only in Ring 0.
  • In virtualization, the VMM/hypervisor needs control of Ring 0.
  • The guest OS cannot safely run with full hardware privilege, so it is often de-privileged or executed in a special hardware-assisted mode.
  • Some x86 sensitive instructions behaved differently outside Ring 0 instead of trapping cleanly, which made classic trap-and-emulate virtualization difficult.

Solutions: Binary translation rewrites problematic instructions; paravirtualization modifies the guest OS to make hypercalls; hardware virtualization adds root/non-root modes so the guest OS can run as if privileged while the hypervisor remains in control.

Q24
What are namespaces with respect to containers? Explain PID and UTS namespaces.
NewUnit 2
▼

Namespaces are Linux kernel features used by containers to isolate global system resources. A namespace makes a process group see its own instance of a resource, even though it is running on the same physical host as other processes.

  • PID namespace: Isolates process identifiers. Processes inside a container see their own process tree and are not aware of processes outside their namespace.
  • UTS namespace: Isolates hostnames and domain names, allowing multiple containers on the same host to appear to have different host identities.
  • MNT namespace: Isolates mount points and filesystem views.
  • IPC namespace: Isolates inter-process communication resources.
  • NET namespace: Gives each container its own network interfaces, routing tables, and ports.
  • USER namespace: Maps users and group IDs separately inside the namespace.
Docker creates namespaces when a container is created; cgroups complement namespaces by limiting CPU, memory, and other resource usage.
Q25
Explain the Popek and Goldberg virtualization requirements. Does classic x86 satisfy them?
AddedUnit 2
▼

Popek and Goldberg defined the conditions for an architecture to support efficient virtualization. A virtual machine monitor should provide:

  • Equivalence: A program running inside the VM should behave essentially like it would on real hardware.
  • Resource control: The VMM must remain in complete control of CPU, memory, and I/O resources.
  • Efficiency: Most non-privileged instructions should run directly on hardware without VMM intervention.

The key theorem says an architecture is classically virtualizable if all sensitive instructions are also privileged instructions. Then sensitive operations trap to the VMM, which can emulate them safely.

Classic pre-2005 x86 did not fully satisfy this because some sensitive instructions behaved differently outside Ring 0 without trapping cleanly. This is why x86 virtualization used techniques like binary translation, paravirtualization, and later hardware support such as Intel VT-x and AMD-V.

Q30
What is replication in a distributed environment? Why is it needed? Explain the different types of replication techniques based on number of leaders (single-leader, multi-leader, leaderless).
Most AskedUnit 3
▼

Replication means keeping multiple copies of the same data on different nodes (potentially in different locations).

Why Replication?

  • Keep data geographically closer to users → reduced latency.
  • Fault tolerance / high availability—continue working even if some nodes fail.
  • Scale out read throughput across multiple machines.

1. Single-Leader Replication (Leader-Based)

One replica is designated the leader. All write requests go to the leader. The leader writes to its local storage and sends a replication log to followers. Followers apply the log in the same order. Reads can go to any replica (though may be slightly stale).

Examples: PostgreSQL, MySQL with replication, MongoDB primary-secondary.

Limitation: Replication lag—followers may serve stale data; leader is a bottleneck for writes.

2. Multi-Leader Replication

Multiple leaders each accept writes. Leaders replicate changes to each other and to followers. Useful in multi-datacenter deployments (one leader per datacenter). Reduces latency for writes.

Challenge: Write conflicts—when the same data is modified on two different leaders concurrently, conflicts must be resolved.

3. Leaderless Replication

Any replica can accept writes. Clients write to multiple replicas (quorum write: typically W out of N nodes must confirm). Clients read from multiple replicas and use version numbers to determine the latest value (quorum read: R out of N nodes).

If W + R > N, there is guaranteed overlap, ensuring at least one node has the latest value.

Stale reads are repaired through read repair (client updates stale replica during read) and anti-entropy (background process syncs replicas).

Examples: Apache Cassandra, Amazon DynamoDB, Riak.

Q31
What is the purpose of rebalancing partitions? Explain: Fixed Number of Partitions, Dynamic Partitioning, and Partitioning Proportional to the Nodes.
Most AskedUnit 3
▼

Rebalancing Partitions — Purpose

Rebalancing is the process of moving data between nodes when the cluster configuration changes (nodes added/removed, hardware failures, data growth). The goals are:

  • Distribute load (data and requests) fairly across nodes after changes.
  • Continue accepting reads and writes while rebalancing is in progress.
  • Move only the minimum necessary data to minimize network/disk load.

1. Fixed Number of Partitions

Create many more partitions than nodes (e.g., 1000 partitions for 10 nodes = 100 partitions/node). When a new node is added, it steals a few partitions from each existing node. Partition boundaries don't change; only assignment changes.

Advantage: Simple; partition count doesn't change. Disadvantage: Must choose partition count ahead of time—too high wastes resources, too low means big partitions and expensive rebalancing.

2. Dynamic Partitioning

Partitions grow and split based on data size. When a partition exceeds a threshold (e.g., 10GB), it's split into two. When data is deleted, partitions can be merged. The number of partitions scales with total data volume.

Advantage: No need to pre-configure partition count; adapts to data. Disadvantage: Initially one partition means all requests go to one node until first split occurs (mitigated with pre-splitting).

3. Partitioning Proportional to the Nodes

Fixed number of partitions per node (e.g., 150 partitions per node). When a new node joins, it randomly picks that many partitions to split, takes half of the data, and keeps the other half in place. Total partition count grows with the number of nodes.

Used in: Cassandra, Ketama. Advantage: Partition sizes remain stable as cluster grows. Disadvantage: Random splitting can lead to unfair data distribution.

Q32
What is a consistency model? Explain Strict, Sequential, Causal, and PRAM (Pipelined RAM) consistency models.
Most AskedUnit 3
▼

A consistency model defines the rules for when and how updates to shared data become visible to different processes in a distributed system. Stronger consistency models are easier to reason about but harder to implement.

1. Strict Consistency (Linearizability)

The strongest model. Any read on a data item X must return the value of the most recent write to X, based on absolute (real-world) time. All operations appear instantaneous and in global time order.

Implication: Effectively impossible to guarantee in a distributed system (violates CAP). Only achievable on a single processor or with atomic transactions.

2. Sequential Consistency

The result of any execution is the same as if operations of all processes were executed in some sequential order, and the operations of each individual process appear in that sequence in the order specified by its program. All processes see the same global order of operations, though that order may differ from real-world time order.

Example: If process P1 writes A=1 then B=2, all processes see A=1 before B=2, but another process's write might appear between them.

3. Causal Consistency

Writes that are causally related must be seen by all processes in the same order. Concurrent writes (with no causal relationship) may be seen in different orders by different processes. Causally related means: if one event (write) may have influenced another, all processes must agree on their order.

Weaker than sequential but stronger than eventual consistency.

4. PRAM (Pipelined RAM) Consistency

Writes done by a single process are seen by all other processes in the order in which they were issued, but writes from different processes may be seen in different orders by different processes. Each process's writes appear in order, but interleaving between different processes may vary.

This is weaker than causal consistency. Easy to implement efficiently as it only requires FIFO ordering of writes from the same source.

Ordering of strength (strongest → weakest): Strict → Sequential → Causal → PRAM → Eventual
Q33
What does the CAP theorem state? Briefly explain the 3 properties. How would you choose a database for your application based on the CAP theorem?
Most AskedUnit 3
▼

CAP Theorem

The CAP theorem states that it is impossible for a distributed data store to simultaneously provide all three of the following guarantees. At most two can be strongly supported at the same time:

1. Consistency (C)

Every read receives the most recent write or an error. All nodes see the same data at any given time. A system has consistency if every read returns the latest successfully written value.

2. Availability (A)

Every request receives a (non-error) response, without guarantee that it contains the most recent data. Every working node returns a valid response to any request.

3. Partition Tolerance (P)

The system continues to operate despite an arbitrary number of network partitions (message losses or delays between nodes). In a distributed system, network partitions are inevitable, so P must always be tolerated.

Since network partitions (P) always occur in distributed systems, the real trade-off is between Consistency (CP) and Availability (AP) when a partition occurs.

Choosing a Database Based on CAP

ChoiceBehaviorUse WhenExamples
CP (Consistency + Partition Tolerance) Rejects requests to avoid returning inconsistent data during a partition. May be unavailable during partition. Financial transactions, banking, payment systems—where data accuracy is critical. HBase, ZooKeeper, MongoDB (in strong consistency mode), PostgreSQL
AP (Availability + Partition Tolerance) Returns potentially stale data during partition rather than failing. Eventually consistent. Social media feeds, shopping carts, DNS—where availability is more important than perfect consistency. Apache Cassandra, CouchDB, DynamoDB, Riak

Note: CA (Consistency + Availability without partition tolerance) is not realistic for distributed systems—partitions always happen over a network. CA applies to single-node systems.

Q37
Explain transactions in distributed systems and the Two-Phase Commit protocol.
AddedUnit 3
▼

A transaction is a unit of work that should preserve ACID properties: atomicity, consistency, isolation, and durability. In distributed systems, one transaction may involve multiple nodes or services, so commit/abort must be coordinated.

Two-Phase Commit (2PC)

  • Coordinator: Controls the transaction decision.
  • Participants: Nodes/services that hold part of the data being updated.
  • Phase 1 - Prepare/Vote: Coordinator asks every participant if it can commit. Each participant writes enough state to commit later and votes yes/no.
  • Phase 2 - Commit/Abort: If all vote yes, the coordinator sends commit. If any vote no or timeout occurs, it sends abort.

2PC gives atomic commitment across nodes, but it can block if the coordinator fails at the wrong time. For microservices, Saga/compensating transactions are often preferred when long-running distributed transactions are not practical.

Compare P2P and Master-Slave (Client-Server) distributed system architectures, including advantages and limitations of each.

Peer-to-Peer (P2P) Architecture

Every node acts as both a client and a server. All nodes are equal—no hierarchy. Nodes join/leave autonomously; the system is self-organizing with distributed control. No node has a global view of the system.

Advantages:

  • Load is naturally distributed.

Limitations:

  • Security is harder to enforce—each peer has its own data.
  • Decision making becomes harder without a central authority.
  • Difficult to manage effectively at scale.
  • Logical paths don't match physical paths, leading to higher latency.

Advantages:

  • Centralized control simplifies management and security.
  • Strong consistency easier to achieve.
  • Well-understood and predictable behavior.

Limitations:

  • Master is a single point of failure (SPOF).
  • Master is a potential performance bottleneck.
  • Less resilient if master fails.
Cloud practice: Cloud systems typically use client-server (master-slave) architecture with centralized management in a single administrative domain, given the manageability, security, and consistency requirements. P2P is used selectively (e.g., Amazon Aurora multi-master).

Most AskedUnit 4
▼

Fault-Tolerant System

A fault-tolerant system is a system designed to continue operating correctly even when some of its components fail. It achieves this through redundancy, failover mechanisms, and careful error handling.

Types of Failures

  • Crash/Fail-Stop: A node stops responding entirely. Easiest to detect and handle.
  • Omission Fault: A node fails to send or receive messages (lost messages).
  • Timing Fault: A node responds but outside the expected time window.
  • Arbitrary/Byzantine Fault: A node behaves incorrectly in unpredictable ways (may send wrong data, corrupt data). Hardest to handle.

MTBF and MTTR Calculation

Given: Total time = 75 hours, Downtime = 60 min = 1 hour, Number of failures = 6.

Total uptime = 75 - 1 = 74 hours

MTBF = Total Uptime / Number of Failures = 74 / 6 ≈ 12.33 hours
MTTR = Total Downtime / Number of Failures = 60 / 6 = 10 minutes

Failover

Failover is the process of automatically switching to a standby/backup system when the primary fails. Two types:

  • Active-Passive: One active server handles all traffic; a standby takes over on failure. Simpler but wasteful (standby idle).
  • Active-Active: Multiple active servers share traffic; on failure, remaining servers absorb the load. Better utilization.

Failure Detection

Heartbeat: Nodes periodically send heartbeat messages to a monitor. If heartbeat is not received within a timeout, the node is considered failed.

Probing: A monitoring node actively polls (probes) other nodes to check if they are alive.

Dual-Scheme Strategy: Combines heartbeat and probing. Heartbeat detects failure passively; probing actively confirms before declaring failure. Reduces false positives (declaring a slow-but-alive node as failed).

What is the purpose of Leader Election in distributed computing? Explain the Ring Election Algorithm (including worst-case scenario and messages required) and the Modified Ring Election Algorithm. Also explain the Bully Algorithm with best and worst cases.
Most AskedUnit 4
▼

Purpose of Leader Election

In distributed systems, many algorithms require a single coordinator (leader) to manage tasks, maintain consistency, and coordinate resource access. However, if the leader fails, a new leader must be chosen. Leader election algorithms determine which node takes over.

When to elect: At system startup, and when the current leader fails (no response within a timeout).

Ring Election Algorithm

Processes are organized in a logical ring. Messages are sent clockwise.

  1. Any process that notices the leader has failed sends an Election message containing its own id:attr.
  2. Each receiving process compares the arriving id with its own:
    • If arrived id > own id → forward the message unchanged.
    • If arrived id < own id, and this process hasn't sent its own election message → overwrite with own id and forward.
    • If arrived id matches own id → this process wins (its id is highest) → send Elected message.
  3. On receiving Elected: note the new coordinator id, forward, unless you are the coordinator.

Worst Case: The counter-clockwise neighbor of the initiator has the highest id.

Messages = (N-1) + N + N = 3N - 1  |  Turnaround = 3N - 1

Problem: If a process is slow (not crashed), it may be bypassed and not elected even though it has the highest id. Ring reorganization is complex on failures during election.

Modified Ring Election Algorithm

Instead of overwriting the message, each process appends its id:attr to the message. Once the message returns to the initiator, it contains all ids.

  1. Initiator elects the process with the best attribute value from the list.
  2. Sends a Coordinator message; each process appends its id and records the coordinator id.
  3. If the coordinator's id is in the final id-list, election is complete; otherwise, restart.

This handles failures more robustly—failed processes are bypassed. The message count is approximately 2N for a non-faulty election (N for election round + N for coordinator announcement).

Bully Algorithm

All processes know each other's IDs. A process that detects the leader's failure initiates an election by sending an Election message to all processes with higher IDs.

  • If no reply within timeout → the initiator declares itself leader and sends Coordinator to all lower IDs.
  • If a reply is received → wait for a Coordinator message from the higher process.
  • A process receiving Election starts its own election (sends to those with higher IDs).

Best case: Process with 2nd highest ID detects failure → sends Coordinator to N-2 processes. Turnaround = 1 message transmission time.

Worst case: Process with lowest ID detects failure → N-1 elections start simultaneously. Message complexity = O(N²). Turnaround ≈ 5 message transmission times.

Q41
What is the problem with a typical distributed lock implementation? Explain the approach (fencing tokens) to overcome the problem. What is distributed locking? Explain optimistic and pessimistic locks.
Most AskedUnit 4
▼

Distributed Lock

A distributed lock is used to provide mutually exclusive access to shared resources across multiple nodes in a distributed system.

Problem with Typical Implementation

Consider: Client 1 acquires lock with expiry 30s. Due to GC pause or slow network, Client 1 is still holding the lock when it expires. Lock manager grants the lock to Client 2. Now both Client 1 (resumed from pause, unaware of expiry) and Client 2 hold the lock simultaneously → race condition → data corruption.

Solution: Fencing Tokens

Every time a lock is granted, the lock service returns a monotonically increasing fencing token (e.g., token 34, then 35). When writing to storage, the client includes its token. The storage server rejects writes with a token lower than the highest it has already seen. Even if Client 1 resumes with stale token 34, the storage rejects it because Client 2 already wrote with token 35.

Pessimistic Locking

A lock is acquired before reading/writing shared data. No other process can access the resource until the lock is released. Suitable when conflicts are likely (high contention).

Downside: Deadlocks possible; reduces concurrency.

Optimistic Locking

No lock is acquired upfront. Each resource has a version number. At commit time, the system checks if the version is still the same as when read. If not (someone else modified it), the transaction is retried.

Suitable for: Low-contention scenarios; higher throughput as no blocking.

What is Zookeeper?

Apache ZooKeeper is an open-source, high-performance coordination service for distributed applications. It provides a centralized infrastructure to maintain configuration information, naming, distributed synchronization, group services, and distributed locking—so developers don't need to build these from scratch.

How It Works

ZooKeeper uses a hierarchical namespace of data registers called znodes (similar to a file system tree). Each znode can store data and may have children.

  • Applications create znodes to coordinate tasks or store shared state.
  • Any node in the cluster can register to be notified of changes to a znode (watch mechanism).
  • ZooKeeper runs as an ensemble (cluster of 3 or 5 servers) for high availability—one server is elected Leader, others are Followers.
  • Client read requests are handled by the connected ZooKeeper server.
  • Client write requests are forwarded to and handled by the Leader.
  • A majority (quorum) of servers must be available for ZooKeeper to function.
  • Each client sends regular heartbeats to the server; if a client fails to respond, its ephemeral znodes are automatically deleted.

Key Benefits

  • Simplicity: Simple, familiar file-system-like interface.
  • High Availability: Ensemble of nodes eliminates single point of failure.
  • Reliability: Uses quorum writes; data is persisted in logs.
  • Wait-Free: Slow/failed clients don't block fast clients.
  • Atomicity: Transactions either succeed or fail completely.

Common Services

  • Naming service: Unique identification for each node.
  • Configuration management: Distributed applications read config from ZooKeeper znodes.
  • Distributed locks & synchronization: Implementing mutual exclusion across nodes.
  • Leader election: Processes use znodes to elect a leader.
  • Group membership: Track which servers are alive in a cluster.

Real-World Usage Contexts

  • Apache Kafka (earlier versions): Used Zookeeper to manage broker metadata and consumer group coordination.
  • Apache HBase: Uses ZooKeeper to track status of distributed data and coordinate the master.
  • Hadoop clusters: Centralized coordination across 500+ commodity servers.

Q46
Explain the following security design patterns: Defense in Depth, Honeypots, Sandboxes, Network Patterns.
Most AskedUnit 4
▼

1. Defense in Depth

This pattern states that defenses should be layered so an attacker must overcome multiple security controls to reach important resources. No single security mechanism is relied upon exclusively.

Cloud example: Remote admin access allowed only through VPN → only from whitelisted IPs → requires one-time password (OTP). An attacker must defeat all three layers.

2. Honeypots

A decoy computer system that appears attractive to attackers. While the attacker wastes time attacking the honeypot (believing it to be a valuable target), security personnel observe the attack patterns and gather intelligence, then attempt to trap and contain the attack.

Cloud context: A honeypot VM is deployed that monitors any suspicious attempt to break into it. Both cloud service providers and cloud customers can deploy honeypots.

3. Sandboxes

Sandboxing executes software in a restricted environment within the OS. Even if an attacker compromises the sandboxed software, they don't get unrestricted access to OS resources. The attacker must additionally break out of the sandbox to gain full control.

Sandboxes provide defense in depth—they limit the blast radius of a compromise. Examples: Browser sandbox, container namespaces, Java SecurityManager.

4. Network Patterns

VM Isolation: New techniques isolate traffic between VMs sharing the same physical hardware (traffic that doesn't cross the switching network). Security features include:

  • Encryption of traffic between VMs on the same host.
  • Tightened security controls on VMs (restrict which ports accept traffic).

Subnet Isolation: VMs grouped into isolated subnets. Traffic between subnets passes through firewalls/security appliances. Limits lateral movement within a network if one VM is compromised.

Q47
What is a DoS attack? Explain with sketches how DoS is different from DDoS. Distinguish EDoS from the above.
Most AskedUnit 4
▼

DoS (Denial of Service)

An attack in which a single attacker floods a target (server/network) with excessive requests or malformed traffic to exhaust resources (bandwidth, CPU, memory), making the service unavailable to legitimate users.

Characteristic: Originates from a single source → easier to detect and block (block that IP).

DDoS (Distributed Denial of Service)

An attack in which many distributed attackers (a botnet—network of compromised machines) simultaneously flood the target. The traffic appears to come from thousands of legitimate sources, making it very difficult to filter.

Key difference: DoS = one attacker; DDoS = thousands of attackers acting in concert. DDoS is far more powerful and harder to mitigate.

EDoS (Economic Denial of Sustainability)

An attack unique to cloud computing. Instead of crashing the service, attackers generate excessive usage of auto-scaling cloud resources, causing the victim to incur massive cloud bills that they cannot sustain economically.

The target service remains available (may even scale up automatically), but the cost becomes unsustainable—the business is harmed economically rather than through outage.

Example: An attacker simulates millions of legitimate users on an auto-scaling web service → the service scales out to hundreds of instances → the owner is charged millions of dollars in cloud costs.

Q48
Explain the following Keystone concepts: Domain, Token. What is Keystone in OpenStack?
Unit 4
▼

What is Keystone?

Keystone is the OpenStack Identity Service. It provides API client authentication, service discovery, and distributed multi-tenant authorization. Every request to an OpenStack service is authenticated via Keystone. It acts as a central registry of users, projects, roles, and services.

Domain in Keystone

A Domain is a high-level organizational grouping in Keystone that contains Projects, Users, and Groups. It enables multi-organization management within a single cloud deployment. Domains allow different organizations to coexist without interfering with each other.

Example: A cloud provider hosting two universities (HighTechUniv, GlobalUniv) creates a separate domain for each. Each domain manages its own users and projects independently.

Token in Keystone

A Token is a time-limited credential issued by Keystone upon successful authentication. After verifying a user's identity (username/password or OAuth), Keystone issues a token. This token is then included in all subsequent API requests to OpenStack services (Nova, Swift, Cinder) to prove identity and authorization.

Tokens expire after a configured TTL (time-to-live), requiring re-authentication.

Other Key Concepts

  • Project: An abstraction (like a tenant/namespace) representing a group of resources belonging to an organization or team.
  • Role: A named set of permissions assigned to users/groups within a project/domain. Used for authorization.
  • User: An individual API consumer. Identified by username + password or OAuth/LDAP credentials.

Cloud Scaling Strategies

Vertical Scaling (Scale Up/Down): Increasing or decreasing the capacity of existing resources (add more CPU/RAM to a server). Simple but has hardware limits; requires downtime in some cases.

Horizontal Scaling (Scale Out/In): Adding more machines/instances to the pool (add more servers). More common in cloud; requires load balancing; no single machine limits. Scale in removes excess machines to reduce cost.

Auto-scaling: Cloud platforms automatically add/remove instances based on metrics (CPU usage, request rate) and policies. Examples: AWS Auto Scaling Groups, Kubernetes HPA (Horizontal Pod Autoscaler).

Explain resource management, scheduling, and resource allocation in a cloud controller.
NewUnit 4
▼

Cloud controllers manage requests for compute, storage, and network resources across many physical machines. They maintain resource state, choose suitable hosts, commit resources when allocation succeeds, and roll back on failure.

  • Resource management: Tracks available capacity and applies policies for allocation, isolation, and utilization.
  • Scheduling: Decides where workloads should run. A server may host many VMs, and a VM may support several applications.

  • Failure handling: If allocation cannot be completed, the request must be rejected or rolled back so resource state stays consistent.
Q51
What is the need for cloud security? Explain physical and virtual cloud security requirements.
NewUnit 4
▼

Cloud security is needed because cloud platforms pool physical resources, virtualize them, expose them over networks, and share them among many tenants. A weakness can affect confidentiality, integrity, availability, compliance, or tenant isolation.

Physical Security

  • Protect data centers, racks, servers, disks, and network devices from unauthorized physical access.
  • Use controlled entry, surveillance, power backup, fire suppression, and disaster recovery processes.
  • Ensure physical redundancy so that hardware failure does not become a single point of failure.

Virtual Security

  • Isolate tenants using hypervisors, containers, namespaces, cgroups, and virtual networks.
  • Secure APIs, dashboards, and orchestration tools with authentication and authorization.
  • Use IAM/Keystone-like identity services for users, tokens, roles, domains, and service access.
  • Encrypt data at rest and in transit; monitor logs and network traffic for attacks.
  • Apply image/container scanning, least privilege, secrets management, and patching.

A system fails when it cannot meet its promised behavior. In distributed systems, failures may be partial and non-deterministic, so designers must explicitly plan how to detect and tolerate them.

Q55
What is distributed consensus? Explain Raft briefly.
AddedUnit 4
▼

Consensus is the problem of getting a group of distributed nodes to agree on a value or system state despite failures, delays, and unreliable communication. It is needed for leader election, replicated logs, membership, distributed locks, and coordination services.

Raft is a consensus algorithm designed to be easier to understand than Paxos. It divides consensus into:

  • Leader election: Nodes elect one leader for a term. The leader handles client requests.
  • Log replication: The leader appends commands to its log and replicates them to followers.
  • Commitment: Once a majority stores an entry, it is committed and applied to the state machine.
  • Safety: Terms, majority voting, and log matching prevent conflicting committed histories.
Zookeeper-like coordination systems use consensus ideas to provide reliable coordination even when some nodes fail.
Q56
Explain checkpointing, application recovery, and strategies for unreliable communication.
AddedUnit 4
▼

Checkpointing records the state of an application or computation at a known point. If the application fails, the latest checkpoint can be restored instead of restarting from the beginning.

Application recovery restarts failed instances and restores them using checkpoints, replicas, or persistent state so service can continue with minimal loss.

Handling Unreliable Communication

  • Timeouts: Avoid waiting forever for a response.
  • Retries with exponential backoff: Retry transient failures while reducing overload.
  • Circuit breakers: Stop calling a failing service temporarily to prevent cascading failures.
  • Bulkheads/isolation: Separate resources so one failing component does not exhaust the whole system.
  • Fallback/cache: Return cached or degraded responses when a dependency is unavailable.
