3.1

Parallel Databases

What is a Parallel Database?

A parallel database system seeks to improve performance through parallelization of operations such as loading data, building indexes, and evaluating queries. It improves processing and I/O speeds by using multiple CPUs and disks in parallel.

Models of Parallelism
🧠
Shared-Memory Single physical address space across all processors. Each processor can directly access others' memory. Large machines use NUMA (Non-Uniform Memory Access) type. Cache access is critical bottleneck.
💾
Shared-Disk Each processor has its own private memory, but all share the disks via a communication network. Appears as NAS (file-level) or SAN (block-level). Controllers manage competing requests.
🔗
Shared-Nothing All processors have their own memory AND disks. All communication is via the network. Most commonly used architecture. Inexpensive (commodity racks) but data transfer between processors is costly.
Query Parallelism
TypeFocusGoalUse Case
Intra-QuerySingle query, broken into parallel sub-tasksReduce response time for one complex queryOLAP (Online Analytical Processing)
Inter-QueryMultiple independent queries run simultaneouslyIncrease overall system throughputOLTP (Online Transaction Processing)
⚙️
Intra-Operation Parallelism — Same operation (scan, sort, join) split and run on different data subsets simultaneously
🔀
Inter-Operation Parallelism — Different operations within the same query plan run concurrently (pipeline or bushy-tree parallelism)
Parallel Algorithms
  • Selection σ(R): Each of p processors examines its local tuples; result distributed same as R — achieves 1/p of uniprocessor time
  • Duplicate Elimination δ(R): Use a hash function to distribute — duplicate tuples land at same processor; apply elimination locally
  • Join R⋈S: Hash tuples of R and S by join attribute Y across p processors; each processor performs a local join on its bucket
  • Aggregation: Hash by grouping attributes across processors; aggregate locally
  • Performance of Join: Total disk I/O = 5(B(R)+B(S))/p per processor vs 3(B(R)+B(S)) on a uniprocessor
3.2

MapReduce & Hadoop

MapReduce Framework

A high-level programming model that achieves parallelism by dividing large datasets into smaller independent chunks. User writes only two functions: map() and reduce(). The framework handles scheduling, monitoring, and inter-machine communication automatically.

1
Map Phase

Indexing and sorting data into key-value pairs. A master controller divides input into chunks; different processors run map() on each chunk.

2
Shuffle Phase

Redistribute mapper output across nodes depending on the key. All values for a given key are sent to the same reducer.

3
Reduce Phase

Produces a summary of previously mapped and shuffled data. Combine/aggregate all values for each key.

Storage Model (HDFS)
  • Massively parallel shared-nothing machines (commodity computers in racks)
  • Data stored in very large files divided into chunks (typically ~128 MB)
  • Each chunk is replicated several times for resiliency against disk failure
  • NameNode: Master node — stores metadata (file names, block locations, permissions). Does NOT store actual data.
  • DataNode: Worker nodes — store actual data blocks; each file divided into blocks distributed across multiple DataNodes

LayerComponentFunction
ManagementAmbariCluster monitoring
AnalyticsPig, Hive, MahoutData analysis and ML
ProcessingMapReduceParallel data processing
StorageHDFSDistributed file storage
DatabaseHBaseNoSQL big data storage
WorkflowOozieJob scheduling

MapReduce Execution Flow
  • Client submits job (JAR file + Mapper/Reducer logic + input/output paths) to Hadoop JobTracker
  • JobTracker splits job into tasks and assigns to TaskTrackers based on data locality (tasks run where data already exists)
  • TaskTrackers execute Map Tasks on local input splits
  • Intermediate results are shuffled and sorted
  • Reduce Tasks process grouped results → final output written to HDFS
✅
Advantages: Parallelism, Scalability, Fault Tolerance, Data Locality, Simplicity (only map/reduce needed)
⚠️
Problems with MapReduce: Slow (hours for queries), Complex programming model, Hundreds of config params, Supports batch only — no real-time streaming

Distributed Databases

Key Definitions
  • DDB (Distributed Database): A collection of multiple logically related databases distributed over a computer network
  • DDBMS: Software that manages a DDB while making the distribution transparent to the user
  • Parallel DB: Data at a single site — uses parallel processing for performance
  • Distributed DB: Data across multiple sites, each managed independently by its own DBMS
FeatureShared-Nothing ParallelDistributed System
LocationSame room / data centerPhysically distant
Network SpeedVery high-speed internalSlower (Internet/LAN/WAN)
Communication CostLow vs disk accessHigh vs computation
UsageParallel DBs, HPCCloud, distributed apps
Homogeneous DDB
  • All sites have identical software
  • Sites are aware of each other and cooperate
  • Appears as a single system to users
  • Each site surrenders some autonomy (schema/software changes)
  • Example: All sites use MySQL
Heterogeneous DDB
  • Different sites use different schemas and software
  • Schema differences → major problem for query processing
  • Software differences → major problem for transaction processing
  • Sites may not even be aware of each other
  • Example: Manufacturing→Oracle, Sales→MySQL, HQ→SQL Server
Data Fragmentation
  • Horizontal Fragment: A subset of tuples (rows) — e.g., all records where DNO=5
  • Vertical Fragment: Keeps only a subset of attributes (columns) — e.g., only SSN and AGE
  • Mixed (Hybrid) Fragment: Combination of both horizontal and vertical fragmentation
  • Fragmentation info stored in a global directory accessed by DDB applications
Data Replication

Storing fragments of data in more than one site. Improves availability; if one site fails, other copies remain accessible.

TypeHow it WorksBest For
Transactional ReplicationSites receive full initial copy, then receive updates as data changes. Consistently replicates each change.Server-to-server environments
Snapshot ReplicationDistributes data exactly as it appears at a specific moment. Does not monitor for updates.Infrequently changed data
Merge ReplicationData from two or more databases combined. Both publisher AND subscriber can independently make changes.Server-to-client, multiple subscribers
Advantages of DDBs & Transparency Types
  • Distribution Transparency: User doesn't know where data is stored
  • Location Transparency: User writes SELECT * FROM Employee — system finds it
  • Naming Transparency: Unique names across system — no need to specify site
  • Replication Transparency: User unaware copies exist
  • Fragmentation Transparency: User unaware of fragments
  • Increased Reliability/Availability: Data replicated at multiple sites
  • Improved Performance: Data kept closer to where it's needed (data localization)
  • Easier Expansion: Adding more data/processors is simpler

Distributed Join Problem

When R and S reside at different nodes, costs must be evaluated carefully:

📊
Example (EMPLOYEE at Site 1, DEPARTMENT at Site 2, Result needed at Site 3):
Option 1: Transfer both to Site 3 → 1,003,500 bytes
Option 2: Transfer EMPLOYEE to Site 2, join, send result to Site 3 → 1,400,000 bytes
Option 3 (BEST): Transfer DEPARTMENT to Site 1, join at Site 1, send result to Site 3 → only 403,500 bytes
Semi-Join Optimization

Only the relevant part of each relation is shipped to the other site. Eliminates "dangling tuples" before full transfer.

1
Project join attributes of S

Send only πY(S) to the site of R — much smaller than full S

2
Compute semi-join at site of R

R ⋉ πY(S) — eliminates all R tuples that won't match

3
Transfer reduced R result to site of S

Only relevant tuples shipped — then perform final join

✅
Semi-join Example Cost: Instead of 403,500 bytes (best direct), semi-join achieves only 340,400 bytes. More efficient when many tuples in R don't participate in join.
Chord Circle (DHT)

For P2P distributed search, nodes are arranged in a virtual circle. Each key K is mapped to the lowest-numbered node Nj where h(K) ≤ j.

  • Finger Table: Each node stores links to nodes at exponentially growing distances (+1, +2, +4, +8, ... steps)
  • Allows lookup in at most m+1 messages (where m = bits in hash) instead of contacting all N nodes
  • Adding a node: Find successor, change predecessor/successor links, redistribute data
  • Node leaving gracefully: Notify predecessor and successor; transfer data to successor
  • Node failure: Replicate data at predecessor and successor; or use clustering (3+ node groups)
3.5

Distributed Transactions & Commit Protocols

Distributed Transactions

In a distributed database, a single transaction may involve operations at several sites. Each component executes at a different site with its own scheduler and log manager.

👨‍💼
Transaction Manager (TM) at each site: maintains log, participates in concurrent execution coordination, ensures serializability locally, executes sub-transactions
🎯
Transaction Coordinator (TC) at each site: starts transactions, distributes sub-transactions to appropriate sites, coordinates final commit/abort decision
⚠️
Key Issue: All sites must agree on the SAME final decision. Either ALL commit or ALL abort. Partial completion is NOT allowed — it would make the database inconsistent.
Two-Phase Commit (2PC)
Phase 1 — Prepare
  • Coordinator logs <Prepare T> and sends "prepare T" to all sites
  • Each site decides to commit or abort its component
  • To commit → enters "pre-committed" state → logs <Ready T> → sends "ready T"
  • To abort → logs <Don't Commit T> → sends "don't commit T"
Phase 2 — Commit/Abort
  • If ALL sites sent "ready T" → coordinator logs <Commit T> → sends "commit T"
  • If ANY site sent "don't commit T" → coordinator logs <Abort T> → sends "abort T"
  • Timeout = site treated as if it sent "don't commit"
  • Each site executes its part and logs accordingly
Three-Phase Commit (3PC)

Solves the blocking problem of 2PC (where participants are stuck if coordinator crashes after Phase 1).

1️⃣
Phase 1: Prepare
Identical to 2PC Phase 1. Sites vote ready/don't-commit.
2️⃣
Phase 2: Pre-Commit
All TMs send votes. Pre-commit state established. Extra safety checkpoint.
3️⃣
Phase 3: DoCommit
Coordinator sends final commit/abort. TMs can decide independently after timeout → non-blocking.
3.6

Distributed Locking & Concurrency

Concurrency Control in DDBs

Ensures multiple transactions across different sites don't interfere with each other. Must be resilient to failures, allow parallelism, minimize communication delays, and preserve data consistency.

⚠️
Without proper control: Lost updates, Dirty reads, Inconsistent retrieval can all occur.
Fully Distributed Locking
  • Each site manages its own lock table
  • Component at a site can only request locks on data at that site
  • Pros: No single point of failure, better scalability, parallel processing
  • Cons: Complex coordination, global deadlock detection is hard, more communication overhead
Centralized Lock Systems
  • One site designated as the lock site for all logical elements
  • Cost: 3 messages per lock (request, grant, release)
  • Cons: Single point of failure; bottleneck under load; if lock site crashes = entire system halts
  • Pros: Simple, easy deadlock detection
Primary-Copy Locking
  • Each logical element X has one copy designated as the primary copy
  • To lock X, transaction sends request to primary copy's site
  • Avoids central bottleneck while keeping simplicity
  • Same 3-message cost per lock (except when transaction and primary copy at same site)
  • Changes at primary site propagate to replicated copies
Quorum Locking (Majority Locking)

When no primary copy exists — all copies are symmetric. Transactions must acquire a certain number of local locks before assuming a global lock.

📖
s (Shared quorum) — Minimum number of copies that must be locked in shared mode to obtain a global shared lock
✏️
x (Exclusive quorum) — Minimum number of copies that must be locked in exclusive mode to obtain a global exclusive lock
Distributed Catalog Management
SchemeHow it WorksProblem
CentralizedEntire catalog at one siteSingle point of failure, availability, bottleneck
Fully ReplicatedComplete catalog at every site; fast local readsAll updates broadcast everywhere; complex update management
Partially ReplicatedEach site stores complete info for local data; may cache remote entriesCached copies may be stale; no consistency guarantee

Peer-to-Peer Distributed Search

P2P Networks

A P2P distributed database is fully decentralized — all nodes are equal peers with no central authority. Each node stores data and acts as both client and server.

FeatureTraditional Distributed DBP2P DB
ControlHead office controls branchesIndependent peers working together
ConsistencyStronger consistencyOften eventual consistency
ScalabilityGoodHighly scalable
Fault toleranceModerateHigh (decentralized)
ExamplesCompany databasesBitTorrent, Blockchain
Chord DHT (Distributed Hash Table)

Nodes arranged in a virtual circle. Each key K is hashed to a value between 0 and 2ᵐ-1. The key-value pair (K,V) is stored at the lowest-numbered node Nj such that h(K) ≤ j.

  • Finger Table: Each node knows nodes at distances +1, +2, +4, +8, +16 ... steps around circle
  • Predecessor & Successor: Each node knows neighbors for simple traversal
  • Lookup complexity: At most m+1 messages for any key (O(log N))
🔍
Search Example: N8 wants h(K)=54. Checks finger table, finds N42 is largest below 54. Sends to N42 → N42 finds N51 → N51 finds N56 has the key. Only ~3 hops vs checking all nodes!

Data locality in Hadoop means tasks are assigned to nodes where the data already exists, avoiding expensive network transfers. The JobTracker assigns tasks to TaskTrackers based on this principle for maximum efficiency.

Primary-Copy Locking distributes the lock function across multiple sites (each logical element has its primary copy at a different site), avoiding the bottleneck of a single central lock site while still maintaining simplicity with 3 messages per lock.

Stream Processing Fundamentals

What is Stream Processing?

The discipline of extracting information from unbounded data — data that is continuously generated and infinite in size (at least theoretically). Instead of waiting for all data, it processes data in real-time or near real-time.

♾️
Unbounded Dataset (Data in Motion)
Infinite / continuously generated. Examples: IoT sensors, social media feeds, stock market data, website click streams. Must be processed continuously.
📦
Bounded Dataset (Data at Rest)
Fixed size — you can count all elements. Examples: stored files, monthly sales reports, CSV datasets. Can be processed via batch processing.
Stream Processing Model
🔌
Source
Where data enters the system: sensors, logs, user events, message queues
⚙️
Processing Component
Core logic: filter, transform, aggregate, analyze
💾
Sink
Destination: databases, dashboards, alerts, storage systems
🔗
Pipeline: One system's sink can become another system's source. Allows building large distributed data workflows: System A → System B → System C.
Transformations vs Aggregations
FeatureTransformationAggregation
Output dependencyNarrow (one input → one output)Wide (many inputs → one output)
ExampleMultiply each number by 2; filter even numbersAverage of last 10 minutes; running total
State neededNone (stateless)Yes (stateful)
Window Aggregations

Instead of processing each event individually, windows group events over a time or count period and apply aggregations.

🪟
Tumbling Windows
Fixed-size, consecutive, NON-overlapping windows. Example: "Max temperature each hour." Independent periods — the most natural windowing.
🎢
Sliding Windows
Two parameters: window length (X) and reporting frequency (Y). Example: "Average share price over last day, reported hourly." Tumbling = special case where X=Y.
Three Types of Time
TypeWhat it isExample
Event TimeWhen the event actually occurred (from source device clock)Sensor records at 10:00 AM → Event Time = 10:00 AM
Ingestion TimeWhen event enters the streaming system (broker timestamp)Event reaches system at 10:00:05 AM
Processing TimeWhen event is processed by the stream engineProcessed at 10:00:08 AM
⚠️
Processing-time windows: Boundaries are well-defined but contents may be wrong — late events missed; events from same real time period may end up in different windows.
✅
Watermarks — A time threshold telling the system "no events older than this timestamp are expected." Closes event-time windows, allowing the system to finalize aggregations. Events older than the watermark are reported in a late-arrivals channel.
Stateful vs Stateless Processing
Stateless Processing
  • Each event processed independently — no memory of past events
  • Simpler, efficient, and easily scalable
  • Examples: Filtering, Mapping, Simple transformations, Splitting streams
Stateful Processing
  • System remembers past data while processing new data
  • Example: Running mean and standard deviation, counting totals
  • More costly; introduces failure concerns (what happens to state if system crashes?)
  • Requires checkpointing and data consistency guarantees

Physical/virtual infrastructure: servers, VMs, base OS. Provides compute power (CPU, RAM, network), forms a cluster of machines.

6

Redis, Cassandra, data warehouses. Stores final output, enables fast querying.

7
Visualization Layer

Dashboards, reports, real-time monitoring. Converts processed data into actionable insights. Shift from static reports → real-time dashboards.

Lambda Architecture

Handles massive data by combining batch + stream processing to balance low latency (fast) with high accuracy (correct).

📦
Batch Layer
Processes entire dataset periodically (daily). Accurate but slow. Maintains master dataset and corrects errors from stream layer.
⚡
Speed Layer (Stream)
Processes real-time data with low latency. May be slightly inaccurate. Provides immediate but approximate results.
🔀
Serving Layer
Combines batch views + stream results. Answers queries. Indexes batch views for low-latency ad-hoc queries.
✅
Benefits: Flexible scaling, automated high availability, business agility, handles both historical and real-time data
⚠️
Challenges: Highly complex — must maintain TWO separate codebases (batch and streaming). Debugging is difficult.

Simpler alternative to Lambda — stream processing only. All data treated as a continuous stream, including historical data (replayed if needed).

Apache Spark & Spark Streaming

Why Spark? (MapReduce Problems Solved)
  • MapReduce queries can take hours — Spark uses in-memory computation → 10–20× faster
  • MapReduce is batch-only — Spark supports real-time streaming
  • MapReduce requires complex Map/Reduce code — Spark offers easy APIs (Python, SQL, Scala, Java, R)
  • Developed by AMPLab, UC Berkeley
  • Stores data in memory using RDDs (Resilient Distributed Datasets) — eliminates expensive disk writes
  • General-purpose cluster-computing platform compatible with Hadoop workloads
Spark Architecture Layers
1
Storage Layer

HDFS, Cassandra, HBase, Amazon S3 — Spark reads from multiple sources

2
Cluster Manager

YARN, Mesos, or Standalone. Manages CPU, memory, node resources.

3
Spark Core

Heart of Spark. Handles task scheduling, memory management, fault tolerance (via RDD lineage DAG).

4
Libraries Layer

Spark SQL (structured queries), MLlib (machine learning), GraphX (graph processing), Spark Streaming (real-time).

Key Spark Concepts
ConceptDescription
In-Memory ProcessingData stored in RAM instead of repeated disk reads. RDDs cached in memory across multiple transformations.
RDD Lineage (DAG)Directed Acyclic Graph tracking transformation history. Enables fault tolerance: lost partitions are recomputed from lineage, not replicated.
Lazy EvaluationTransformations (map, filter) not executed immediately. Build a logical plan. Execution triggered only when an Action is called (count, collect, save).
Cache Hintsdf.cache() — tell Spark to keep data in memory for reuse. If memory is full, Spark spills to disk.
MicrobatchingStream data collected into small fixed-interval batches. Baseline latency = at least the batch interval (typically 1 second minimum).
Polyglot APISpark supports Scala, Java, Python (PySpark), and R languages.
Spark Streaming vs Structured Streaming
Spark Streaming (DStreams)
  • Converts stream into micro-batches at fixed time intervals
  • DStream = sequence of RDDs over time
  • Lazily evaluated, immutable DStreams
  • Older API; simpler but less optimized
  • Needs output operation to trigger execution
Structured Streaming
  • Treats stream as an unbounded, continuously updating table
  • Based on Catalyst Optimizer (rule + cost based)
  • Uses DataFrames/Datasets — SQL-like API
  • Supports event time, watermarking, multiple output modes
  • More optimized; easier for structured data
4.4

Apache Kafka

What is Apache Kafka?

A distributed, high-throughput event streaming platform essential for big data architectures. Acts as a resilient buffer and data pipeline between data sources and processing systems. Decouples producers from consumers so neither needs to know about the other.

Core Kafka Components
📤
Producer (Publisher)
Defines what data to send. Publishes messages to topics.
📥
Consumer (Subscriber)
Subscribes to topics. Receives messages from the communication infrastructure. Does NOT specify who to receive from.
🏛️
Broker
The communication infrastructure. Routes messages from producers to consumers. Multiple brokers form a Kafka cluster.
Topics, Partitions & Routing
  • Topic: A named log on disk (e.g., "/shopping-cart-done"). Producers send to topics; consumers subscribe to topics
  • Topic-Based Routing: Subscribers receive ALL messages on a subscribed topic — supported by Kafka
  • Content-Based Routing: Subscribers define matching criteria — NOT supported by Kafka. Only pattern-based (wildcard) is available
  • Partition: Ordered, immutable sequence of messages within a topic. Each partition replicated across multiple brokers for redundancy.
  • Offset: Each message within a partition has a unique position/offset
  • Publisher decides which partition to write to (round-robin or key-based)
  • Partitions allow logs larger than single disk size and throughput greater than single server
Fault Tolerance (Replication)
  • Leader: Handles all reads and writes for a partition
  • Follower: Replicates leader data; takes over if leader fails (automatic failover)
  • Recommended: Replicas = 3, Quorum = 2
💨
Acks=0 (Async/Fire-and-Forget): No response waited — fastest but risk of data loss
🔐
Acks=all (Sync): Wait until quorum of replicas confirm — safest
Why Kafka is Fast
  • Sequential I/O: Producers append to end of file (sequential write); consumers read in order (sequential read). Disk drives are very fast for sequential operations.
  • Zero Copy I/O: Uses DMA (Direct Memory Access) — OS moves data directly from disk cache to network card. No CPU copying between kernel and user space.
  • Write Batching: Groups messages into batches, reducing network packets and disk operations.
  • Result: Nearly 100,000 messages/second vs traditional messaging systems like RabbitMQ (~20,000)

Multi-Model Databases

What is a Multi-Model Database?

A database that can store, index, and query data in more than one model — combining relational, document, graph, key-value, and other models in one system. Provides a 360° view of customer data across varying formats.

1️⃣
Single Engine
One engine supports all data models natively (e.g., ArangoDB, OrientDB)
🔀
Multi-Engine
Multiple specialized engines; middleware layer integrates them and provides unified query interface (e.g., Azure Cosmos DB, Oracle)

Polyglot Persistence vs Multi-Model DB
🗃️
Polyglot Persistence
Using MULTIPLE SEPARATE databases for different data types. Example: User data → Relational DB, Product catalog → Document DB, Recommendations → Graph DB.
🏢
Multi-Model DB
ONE database handles all models internally. Reduces need for polyglot persistence. ArangoDB/Oracle can handle document + graph + relational in one system.
Challenges of Multi-Model Databases
  • Open Data Model: Difficult common abstraction for all models; heterogeneous data integration is complex
  • Unified Query Language: Graph needs traversal, document needs nested queries, relational needs joins — one language may become too complex
  • Schema Evolution: Managing changes across multiple models; backward compatibility is hard
  • Multi-Model Index: Each model needs different indexing (B+ trees, inverted indexes, adjacency); storage overhead increases
  • Multi-Model Transactions: ACID across models is complex; distributed transactions expensive
  • Memory Management: Different in-memory structures for each model; complex memory management
⚖️
ACID vs BASE in Multi-Model DBs: ACID (Atomicity, Consistency, Isolation, Durability) = strong consistency, slower, suitable for banking. BASE (Basically Available, Soft State, Eventual Consistency) = prioritizes availability/scalability, used in social media/big data.
4.6

Data Warehousing

What is a Data Warehouse?

A subject-oriented, integrated, nonvolatile, time-variant collection of data in support of management's decisions. Holds data extracted from transaction systems, operational stores, and external sources in aggregate/summary form for enterprise-wide analysis and reporting.

  • Subject-Oriented: Organized around major subjects (sales, customers, products)
  • Integrated: Collected from multiple sources, made consistent
  • Nonvolatile: Stable — not frequently changed (read-mostly)
  • Time-Variant: Contains historical data across time periods
ETL Process (Building the Warehouse)
1
Extract

Collect data from multiple heterogeneous sources (Oracle, MySQL, CSV, ERP, CRM) into a staging area

2
Format

Ensure uniform representation — convert date formats, units, and encodings to a standard

3
Clean

Remove missing values, duplicate records, incorrect/invalid data using validation and deduplication

4
Transform

Fit data into warehouse schema (star/snowflake). Convert raw data into fact tables and dimension tables.

5
Load

Initial Load (full first-time load) or Incremental Load (only new/updated data added)

Multi-Dimensional Modeling
⭐
Star Schema
Central fact table surrounded by dimension tables (one table per dimension). Simple, fast queries. Most common for data warehouses.
❄️
Snowflake Schema
Variation of star schema where dimension tables are normalized into a hierarchy. Less redundancy but more complex joins.
📊
Fact Table: Contains the measurable, quantitative data (e.g., sales amount, quantity). Has one tuple per recorded fact with pointers to dimension tables.
📐
Dimension Table: Contains descriptive attributes (e.g., time, product, location, customer). Used to organize and filter fact data.

4.7

Data Mining

What is Data Mining?

The process of discovering meaningful correlations, patterns, and trends by sifting through large amounts of data stored in repositories, employing pattern recognition technologies, statistical and mathematical techniques.

  • Association Rules: "If customer buys video equipment, they also buy another gadget" — correlate presence of items
  • Classification Hierarchies: Classify customers by visit frequency, purchase type — work from existing events to create classes
  • Sequential Patterns: "Camera → photographic supplies (3 months later) → accessory (6 months later)"
  • Segmentation/Clustering: Partition population into groups of similar items/events
Goals of Data Mining
  • Prediction: Analyze buying transactions to predict future purchases under certain discounts
  • Identification: Identify intruders by programs executed, files accessed, CPU time per session
  • Classification: Categorize customers (discount-seekers, loyal regulars, brand-attached shoppers)
  • Optimization: Maximize output (sales, profits) given limited resources under constraints
Frequent Patterns & Apriori Algorithm
📊
Support — Frequency of occurrence of a pattern. How often an itemset appears in the database.
Example: Support(milk → bread) = 3/5 = 0.6
🎯
Confidence — Likelihood that one item is purchased when another is. % of transactions containing A that also contain B.
Example: Confidence(milk → bread) = 0.6/0.8 = 0.75
🔑
Apriori Property (Downward Closure): If an itemset is frequent, ALL of its subsets must also be frequent. If a subset is NOT frequent, we can PRUNE the entire itemset — avoids evaluating all possible combinations.
1
Set Minimum Support threshold

e.g., 40%

2
Find frequent 1-itemsets (L1)

Count each item; remove those below min support

3
Generate candidate k-itemsets, prune, repeat

Combine frequent (k-1) itemsets; use Apriori to prune infrequent ones; find Lk

4
Generate Association Rules

From frequent itemsets, calculate Support and Confidence; select rules above minimum confidence

Recommendation Systems
📄
Content-Based Filtering
Recommends items similar to past preferences. Uses product features and textual descriptions. Computes cosine similarity between user profile vector and item vector.
👥
Collaborative Filtering
Recommends based on opinions of similar users. User-User (find similar users) or Item-Item (find similar items). Does not need item attributes.
🔀
Hybrid Filtering
Combines content-based and collaborative. Weighted average of both scores or combined ranking. Best of both worlds.

Data Lakes, Lakehouses & Data Fabric

What is a Data Lake?

A centralized repository that stores large volumes of data in its native format — structured, semi-structured, and unstructured. Uses low-cost object storage and open formats. Applies schema on READ (not on write).

  • Stores raw data without predefined schema (schema-on-read)
  • Supports fast data ingestion (quick ingest from multiple sources with minimal delay)
  • Enables on-demand processing for analytics, exploration, machine learning
  • Scales efficiently to handle massive volumes

Data Lakehouse

A new paradigm combining the best of data lakes AND data warehouses. Implements data warehouse features (ACID transactions, schema enforcement, query optimization) directly on low-cost data lake storage.

Data Fabric

A modern architecture designed to democratize data access across an organization. A loosely coupled collection of distributed services providing the right data in the right shape at the right time from heterogeneous sources, across any cloud and on-premises platforms.

  • Distributed & Loosely Coupled: Network of independent but connected data nodes
  • Works Across Hybrid & Multicloud: On-premise + AWS + Azure + others
  • Intelligent & Automated: Automates integration, movement, transformation
  • Self-Service Access: Users access data without deep technical knowledge
  • Handles Heterogeneous Data: Transactional + analytical + structured + unstructured
  • Non-Functional Compliance: Performance, security, governance, cost efficiency

Q1.What is a Tumbling Window in stream processing?
AA window that overlaps with the previous window by half its size
BFixed-size, consecutive, non-overlapping windows where each period is independent from previous ones
CA window that slides every few seconds while covering a longer period
DA window that groups events by count rather than by time
Tumbling windows are fixed-size, consecutive, and NON-overlapping. Each period follows the previous without overlap (e.g., 0-60min, 60-120min, 120-180min). Sliding windows are a superset where the reporting frequency < window size.
Q2.What is a Watermark in event-time stream processing?
AA security marker added to streamed data for copyright protection
BA threshold for maximum throughput in a data pipeline
CA time threshold telling the system "no events older than this timestamp are expected" — used to close event-time windows
DThe minimum delay between processing two consecutive events
A watermark closes the open boundary of event-time windows by declaring "no more events older than this time will arrive." This allows the system to finalize aggregations. Events older than the watermark are treated as late arrivals.
Q3.In Lambda Architecture, what is the purpose of the Speed Layer?
ATo process real-time data with low latency, providing immediate but possibly approximate results
BTo reprocess the entire historical dataset accurately every day
CTo answer user queries by combining batch and stream results
DTo store and index master datasets for archival purposes
The Speed Layer (stream layer) processes only recent, real-time data not yet covered by the batch layer. It provides low-latency but possibly slightly inaccurate results. The batch layer eventually corrects any errors made by the speed layer.
Q4.What makes Apache Spark 10-20× faster than traditional MapReduce?
AIt uses more processors and larger cluster sizes
BIt skips the shuffle phase of MapReduce
CIt uses a better compression algorithm for data storage
DIt stores RDDs in memory (in-memory computation), eliminating expensive intermediate disk writes
Spark's key innovation is in-memory computation via RDDs (Resilient Distributed Datasets). Instead of writing intermediate results to disk between each MapReduce step, Spark keeps data in RAM, drastically reducing I/O overhead.
Q5.What is a Kafka Partition?
AA virtual machine in the Kafka cluster
BAn ordered, immutable sequence of messages within a topic; replicated across brokers for redundancy
CA subset of consumers that receive the same messages
DThe maximum size of a single Kafka message
A Kafka partition is an ordered, immutable sequence of messages within a topic. Partitions allow topics to scale beyond a single disk/server and enable parallel throughput. Each partition is replicated across multiple brokers. Publishers decide which partition to write to (round-robin or key-based).
Q6.What is the difference between Data Lakes and Data Warehouses regarding schema?
ABoth use schema-on-read; warehouses are just more optimized
BData lakes use schema-on-write; data warehouses use schema-on-read
CData lakes use schema-on-read (no predefined schema); data warehouses use schema-on-write (schema defined before loading)
DData lakes have rigid schemas; data warehouses are flexible
Data warehouses enforce schema BEFORE data is written (schema-on-write) — data must conform to predefined structure. Data lakes store raw data in native format WITHOUT a predefined schema (schema-on-read) — schema is applied only when the data is queried.
Q7.In the Apriori algorithm, what does the Downward Closure Property state?
AIf an itemset is frequent, then all of its subsets must also be frequent; if a subset is infrequent, we can prune the superset
BFrequent itemsets always appear at the beginning of transaction logs
CConfidence is always higher than support for any association rule
DAny itemset that meets minimum confidence is also frequent
The Apriori Property (Downward Closure): If {A,B,C} is frequent, then {A,B}, {A,C}, {B,C}, {A}, {B}, {C} must ALL be frequent. Contrapositive: if any subset is infrequent, the full itemset cannot be frequent → we can prune it without checking, saving enormous computation.
Q8.What distinguishes Kappa Architecture from Lambda Architecture?
AKappa uses a batch layer for accuracy while Lambda is stream-only
BLambda is simpler because it only has one processing layer
CKappa cannot handle historical data; Lambda can
DKappa uses stream processing only with a unified codebase; Lambda uses separate batch and stream layers with two codebases
Kappa Architecture uses stream processing ONLY — all data is treated as streams, including historical data (replayed if needed). Lambda has both a batch layer (accurate, slow) and a speed layer (fast, approximate), requiring two separate codebases to maintain.
Q9.In a Star Schema for Data Warehousing, what does the Fact Table contain?
ADescriptive information about dimensions like time, location, and customer
BMeasurable, quantitative data (e.g., sales amounts, quantities) with pointers to dimension tables
CThe raw, unprocessed source data before ETL
DMetadata about the data warehouse structure itself
The Fact Table contains measurable/quantitative data (e.g., sales amount, quantity sold, revenue). It has one tuple per recorded fact and contains foreign keys (pointers) to surrounding Dimension Tables, which hold descriptive attributes like time, product, location, customer.
Q10.What is Polyglot Persistence?
AA single database that supports multiple query languages
BUsing one multi-model database to handle all data types in an application
CUsing multiple separate, specialized data storage technologies for different data types within one application
DTranslating data between different database formats automatically
Polyglot persistence = using MULTIPLE DIFFERENT databases for different data storage needs within a single application, chosen based on how data is used. Example: User data → MySQL, Product catalog → MongoDB, Recommendations → Neo4j. It's "using the right tool for the right job."
Q11.What is the ROLL-UP operation in OLAP?
ASummarizing data with increasing generalization (e.g., Day → Month → Year)
BIncreasing levels of detail in data analysis (going from Year to Day)
CRotating the perspective of the data cube for cross-tabulation
DSelecting a single value from a specific dimension
Roll-up aggregates data at a higher level of generalization. Day → Month → Year is rolling up time. City → State → Country is rolling up geography. Drill-down is the reverse (more detail). Together they allow navigating the data cube's hierarchy.
Q12.What does RDD stand for in Apache Spark, and why is it important?
ARapid Data Distribution — important for network-efficient data transfer
BReplicated Disk Dataset — important for fault tolerance via disk backup
CReal-time Data Descriptor — important for streaming metadata management
DResilient Distributed Dataset — a fault-tolerant, in-memory data structure tracking transformation lineage to enable recomputation on failure
RDD = Resilient Distributed Dataset. "Resilient" = fault-tolerant via lineage (can recompute lost partitions). "Distributed" = data partitioned across cluster. "Dataset" = a collection of records. RDDs are immutable and lazily evaluated. Their lineage DAG is the key to Spark's speed and fault tolerance.
