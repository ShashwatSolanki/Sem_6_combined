01 Elucidate the four main pillars of Object-Oriented Programming: Abstraction, Encapsulation, Inheritance, and Polymorphism.
JavaOOP

1. Abstraction

Abstraction means representing essential features of an entity while hiding the irrelevant implementation details. It lets you model real-world concepts in a simplified way. In Java, abstraction is achieved via abstract classes and interfaces — abstract classes allow partial abstraction and interfaces allow 100% abstraction.

abstract class Animal {
    public abstract void animalSound(); // abstract method — no body
    public void sleep() { System.out.println("Zzz"); }
}
class Dog extends Animal {
    public void animalSound() { System.out.println("Woof"); }
}

2. Encapsulation

Encapsulation bundles data (attributes) and the methods that operate on that data within a single unit (class), and restricts direct access to internal state using access modifiers (private, protected, public). External code interacts only through well-defined getter/setter methods, protecting the internal representation.

class Person {
    private String name; // hidden
    public String getName() { return name; }
    public void setName(String n) { this.name = n; }
}

3. Inheritance

Inheritance is the mechanism by which a child (subclass) acquires the attributes and behaviours of a parent (superclass). It promotes code reuse and represents "is-a" relationships. In UML, shown as a solid line with a hollow triangle pointing to the superclass.

class Vehicle { void start() { System.out.println("Starting"); } }
class Car extends Vehicle { void honk() { System.out.println("Beep"); } }

4. Polymorphism

Polymorphism ("many forms") allows a single interface to represent different underlying forms. There are two main types:

  • Compile-time (overloading / ad-hoc): Same method name with different parameter signatures in the same class.
  • Runtime (overriding / inclusion): A subclass provides a specific implementation for a method already defined in its superclass; the correct version is resolved at runtime via dynamic dispatch.
class Shape { void draw() { System.out.println("Shape"); } }
class Circle extends Shape {
    @Override void draw() { System.out.println("Circle"); }
}
02 Write short notes on the different types of relationships in a UML Class Diagram: Association, Aggregation, Composition, Qualified Association, Generalization, Dependency, and Realization.
Class Diagram

Association

A structural relationship between two classes indicating that objects of one class are connected to objects of another. Drawn as a plain solid line; can be unidirectional (open arrowhead) or bidirectional. Annotated with multiplicity (e.g., 1..*). Example: Student ↔ Instructor.

Aggregation ("has-a", weak)

A special association representing a whole–part relationship where the part can exist independently of the whole. Drawn as a solid line with a hollow diamond at the whole end. Example: Department ◇— Professor. Professors survive even if a department is dissolved.

Composition ("has-a", strong)

A stronger form of aggregation where the part cannot exist without the whole — lifecycle of the part depends on the whole. Drawn with a filled diamond at the whole end. Example: Car ◆— Engine. If the car is destroyed, the engine instance ceases to exist as well.

Qualified Association

An association with a qualifier — a key or discriminator attribute placed in a small box on the association end — that identifies or reduces the multiplicity on the other end. Example: Bank [accountNumber] → Account. A specific account number uniquely identifies one Account from the Bank's perspective, reducing multiplicity from many to one.

Generalization (Inheritance)

An "is-a" relationship from subclass to superclass. Child inherits parent attributes/operations. Drawn as a solid line with a hollow triangle arrowhead pointing to the parent. Example: Car → Vehicle.

Dependency

A weak relationship indicating that one class uses another (e.g., as a method parameter) but does not store it as an attribute. A change in the used class may affect the dependent class. Drawn as a dashed arrow. Example: Person --→ Book (Person has hasRead(Book) method).

Realization (Interface Implementation)

A relationship between a class and an interface where the class guarantees to implement all operations declared in the interface. Drawn as a dashed line with a hollow open arrowhead pointing to the interface. Example: AudioPlayer - - ▷ «interface» MediaPlayer.

Use Case Relationship Types

06 Write short notes on the elements of a UML Component Diagram (Port, Dependency, Component, Interface).
Component Diagram

Component

A replaceable and executable piece of a system whose implementation is hidden from the external environment. A component provides and requires interfaces to function. Notated as a rectangle with the «component» stereotype or a small component icon in the corner.

Interface

A named set of public features (operations) that a component exposes or requires. Two types: Provided Interface (lollipop notation — what the component offers) and Required Interface (socket notation — what the component needs from others).

Port

A specific interaction point on a component through which the component communicates with its environment. A port is drawn as a small square on the boundary of the component rectangle. It groups related interfaces and can have both provided and required interfaces.

Dependency

A "uses" relationship between components indicating that one component depends on services provided by another. Drawn as a dashed arrow (→) from the dependent component to the component it depends upon. A change in the depended-upon component may affect the dependent one.

07 Write short notes on State Diagram — State, Event, Guard Condition, Transition, Synchronization/Splitting.
State Diagram

State

A state represents a situation during the life of an object where it satisfies some condition, performs some activity, or waits for an event. Drawn as a rounded rectangle. An initial state is a filled circle; a final state is a filled circle inside a larger circle.

Event

An event is an occurrence that triggers a transition from one state to another. Events are labelled on transition arrows. Example: borrow() event on a Book object moves it from "Available" to "OnLoan".

Guard Condition

A Boolean expression in square brackets that must evaluate to true before a transition fires. Example: [daysOverdue > 365] triggers the "Lost" transition for a library book.

Transition

Shown as a solid arrow between states, labelled with the triggering event and optional guard condition and action: event [guard] / action. A self-transition (looping arrow on same state) is also valid.

Synchronization and Splitting (Fork/Join)

Used in state diagrams with concurrent (composite) states. A fork (splitting bar) splits one incoming flow into multiple parallel sub-states. A join (synchronization bar) merges multiple concurrent sub-states back into one. Represented as a short, heavy horizontal or vertical bar.

11 Describe the Analysis and Design phases in the Object-Oriented approach. Distinguish OO approach from Procedure-Oriented approach.
OOP

OO Analysis (OOA)

OOA involves understanding and modelling the problem domain in terms of objects, classes, and their relationships. Activities include identifying actors and use cases, discovering domain classes (using noun-phrase or common class patterns approaches), and capturing structural relationships via class diagrams and dynamic behaviour via activity/sequence diagrams.

OO Design (OOD)

OOD refines the analysis model into a technical blueprint for implementation — assigning responsibilities to classes using GRASP principles, designing interactions between objects (sequence diagrams), applying design patterns (Singleton, Factory, etc.), and defining system architecture (component and deployment diagrams).

OO vs Procedure-Oriented Programming

  • Focus: POP focuses on functions/procedures; OOP focuses on objects/data.
  • Data access: POP data is global and freely accessible; OOP data is encapsulated and hidden.
  • Approach: POP is top-down decomposition; OOP is bottom-up with objects collaborating.
  • Reusability: POP has limited reuse; OOP promotes reuse via inheritance and composition.
  • Real-world mapping: OOP naturally maps to real-world entities; POP does not.
  • Examples: POP — C, FORTRAN, COBOL; OOP — Java, C++, Python.

12 What are the three types of constructors in Java? Give an example of each.
Java

A constructor initialises an object when it is created. It has the same name as the class and has no explicit return type.

1. Default Constructor (No-arg)

Has no parameters. Initialises instance variables to default values (0, false, null). If no constructor is defined, Java automatically provides one.

class Student {
    int id; String name;
    Student() { // default constructor
        id = 0; name = "Unknown";
    }
}

2. Parameterised Constructor

Accepts parameters to initialise the object with specific values. Uses this to resolve name conflicts.

class Student {
    int id; String name;
    Student(int id, String name) { // parameterised
        this.id = id;
        this.name = name;
    }
}

3. Copy Constructor

Takes an object of the same class as a parameter and creates a new object with the same state. Prevents unwanted reference sharing.

class Student {
    int id; String name;
    Student(Student s) { // copy constructor
        this.id = s.id;
        this.name = new String(s.name); // deep copy
    }
}
13 What is the need for the Garbage Collector in Java?
Java

Java's Garbage Collector (GC) is a background process that automatically identifies and removes objects from heap memory that are no longer referenced by any active part of the program, then reclaims that memory space for future allocations.

Why It Is Needed

  • Prevents memory leaks: Without GC, unreferenced objects would accumulate and exhaust available heap memory.
  • Eliminates manual memory management: Unlike C/C++ (where programmers call free()), Java automates deallocation, reducing bugs like dangling pointers and double-free errors.
  • Improves productivity: Developers focus on application logic rather than memory lifecycle management.

finalize() Method

Before an object is garbage collected, the JVM calls its finalize() method (if defined), allowing cleanup tasks like closing database connections or releasing network resources. However, its execution is not guaranteed.

protected void finalize() {
    // close DB connections, release locks, etc.
}
14 Give an example for Method Overloading and Method Overriding. State the differences.
Java

Method Overloading (Compile-time Polymorphism)

Multiple methods in the same class with the same name but different parameter lists (number or type of parameters).

class Calculator {
    int add(int a, int b)         { return a + b; }
    double add(double a, double b){ return a + b; }
    int add(int a, int b, int c)  { return a + b + c; }
}

Method Overriding (Runtime Polymorphism)

A subclass provides a specific implementation for a method already defined in the parent class. Same name, same parameters, same return type. The @Override annotation is recommended.

class Animal   { void sound() { System.out.println("Generic sound"); } }
class Dog extends Animal {
    @Override
    void sound() { System.out.println("Woof"); }
}

Key Differences

  • Location: Overloading — same class; Overriding — parent & child classes.
  • Resolution: Overloading — compile time; Overriding — runtime.
  • Parameters: Overloading — must differ; Overriding — must be identical.
  • Inheritance: Overloading — not required; Overriding — requires inheritance.
  • Return type: Overloading — can differ; Overriding — must be same (or covariant).
  • Static methods: Static methods can be overloaded but not overridden (they are hidden).
15 State any six differences between an Abstract Class and an Interface in Java.
Java
  • Instantiation: Neither can be instantiated directly. An abstract class can have concrete (non-abstract) methods; an interface methods are all public and abstract by default (Java 8+ allows default/static methods).
  • Multiple inheritance: A class can implement multiple interfaces (supported); a class can extend only one abstract class (not supported in Java).
  • Constructor: Abstract classes can have constructors (called via super()); interfaces cannot have constructors.
  • Variables: Abstract classes can have instance variables of any access modifier; interface variables are implicitly public static final (constants only).
  • Access modifiers for methods: Abstract class methods can be private, protected, public; interface methods are always public.
  • Purpose: Abstract class represents what an object IS (partial implementation, shared state); interface represents what an object CAN DO (a contract/capability).
  • Speed: Abstract classes are slightly faster (no extra indirection); interfaces involve an extra lookup.
16 What are Generic classes in Java? Write an example program demonstrating a generic class.
Java

Generics allow classes, interfaces, and methods to operate on objects of various types while providing compile-time type safety. A type parameter (e.g., <T>) is used as a placeholder for an actual type supplied when the class is instantiated.

Benefits

  • Eliminates the need for explicit type casting.
  • Catches type errors at compile time, not runtime.
  • Enables code reuse across different data types.
// Generic Pair class
class Pair<T, U> {
    private T first;
    private U second;

    Pair(T first, U second) {
        this.first = first;
        this.second = second;
    }
    T getFirst()  { return first; }
    U getSecond() { return second; }
}

public class Main {
    public static void main(String[] args) {
        Pair<String, Integer> p = new Pair<>("Age", 21);
        System.out.println(p.getFirst() + ": " + p.getSecond());
        // Output: Age: 21
    }
}
17 Write about the three access specifiers in Java (private, protected, public) and their effects on member variables.
Java
  • private: Accessible only within the same class. Strongest encapsulation. No external class (not even subclasses) can access it directly. Use for all sensitive data.
  • protected: Accessible within the same class, same package, and subclasses (even in different packages). Used to share data with child classes while hiding it from unrelated classes.
  • public: Accessible from anywhere — same class, same package, any package. Widest visibility. Used for methods/attributes that form the public API.
  • (default / package-private): No keyword used; accessible only within the same package.
class Employee {
    public    String name;      // accessible everywhere
    protected String dept;      // accessible in subclasses
    private   double salary;    // only within Employee class

    public double getSalary() { return salary; } // getter for private
}
18 Explain different types of Inheritance in Java with examples.
Java

1. Single Inheritance

One class inherits from exactly one parent class.

class Animal { void eat() { System.out.println("Eating"); } }
class Dog extends Animal { void bark() { System.out.println("Woof"); } }

2. Multilevel Inheritance

A chain: C extends B, B extends A.

class A { void showA() {} }
class B extends A { void showB() {} }
class C extends B { void showC() {} }

3. Hierarchical Inheritance

Multiple classes inherit from a single parent.

class Vehicle { void start() {} }
class Car     extends Vehicle {}
class Truck   extends Vehicle {}

4. Multiple Inheritance (via Interfaces)

Java does not support multiple class inheritance to avoid the diamond problem. However, a class can implement multiple interfaces.

interface Flyable { void fly(); }
interface Swimmable { void swim(); }
class Duck implements Flyable, Swimmable {
    public void fly()  { System.out.println("Flying"); }
    public void swim() { System.out.println("Swimming"); }
}
Note: Hybrid inheritance (combination of above) is also possible in Java through interfaces.
19 Write short notes on: Method Overloading, Static and Instance Members, Abstract Class.
Java

Method Overloading

Defining multiple methods in the same class with the same name but different parameter lists. Resolved at compile-time (compile-time polymorphism). The compiler distinguishes methods by number, type, or order of parameters — not by return type alone.

Static vs Instance Members

  • Static members belong to the class, not any individual object. Shared across all instances. Accessed via ClassName.member. Allocated once in memory when the class is loaded.
  • Instance members belong to each object individually. Each object has its own copy. Accessed via objectRef.member.
class Counter {
    static int count = 0; // shared by all
    int id;               // unique per object
    Counter() { count++; this.id = count; }
}

Abstract Class

A class declared with the abstract keyword that cannot be instantiated directly. It serves as a template for subclasses. May contain abstract methods (no body) that must be overridden by concrete subclasses, as well as concrete methods. Enables partial abstraction.

abstract class Shape {
    abstract double area();       // must be implemented
    void display() {              // concrete method
        System.out.println("Area: " + area());
    }
}

20 Explain the GRASP principles: Creator, Information Expert, Low Coupling, High Cohesion, Controller, Polymorphism, Indirection, and Pure Fabrication.
GRASP

Creator

Problem: Who creates a new instance of class A?
Solution: Assign creation responsibility to the class B that: contains A, aggregates A, has the initializing data for A, or records A. Promotes low coupling by keeping creation close to usage. Example: a Sale creates SalesLineItem objects.

Information Expert

Problem: What is the basic principle for assigning responsibilities?
Solution: Assign a responsibility to the class that has the information needed to fulfill it. Example: Sale is responsible for knowing the grand total because it has access to all SalesLineItems.

Low Coupling

Problem: How to reduce the impact of change in one class on others?
Solution: Assign responsibilities so that coupling (dependency) remains low. Prefer composition, dependency injection, and programming to interfaces. Low coupling leads to systems that are easier to maintain and reuse.

High Cohesion

Problem: How to keep classes focused and manageable?
Solution: Assign responsibilities so that cohesion remains high — a class should have a focused, related set of responsibilities. Highly cohesive classes are easier to understand, maintain, and reuse.

Controller

Problem: Who handles system events from the UI layer?
Solution: Assign system-event handling to either: (a) a Façade Controller representing the entire system/subsystem, or (b) a Use-Case Controller for a specific use-case scenario. The controller delegates work to domain objects rather than doing it itself. Prevents UI objects from being directly coupled to business logic.

Polymorphism

Problem: How to handle alternative behaviours based on type?
Solution: Assign behaviour variation to the types for which the behaviour varies, using polymorphism. Avoids large if/switch type-checking blocks. Example: different Payment subclasses override a common process() method.

Indirection

Problem: How to avoid direct coupling between components?
Solution: Assign responsibility to an intermediate object to mediate between other components. The intermediary decouples the original components. Example: a Controller class between UI and domain model.

Pure Fabrication

Problem: When no domain class is a good fit for a responsibility (assigning it would violate high cohesion or low coupling), who gets it?
Solution: Create a class that does not represent a concept in the problem domain — a "made-up" service class — solely to achieve a clean design. Example: a DatabasePersistenceService class to handle DB operations, keeping domain classes clean.

21 Explain the SOLID design principles with an example for each.
SOLID

S — Single Responsibility Principle (SRP)

A class should have only one reason to change — i.e., one primary responsibility. Separating concerns makes classes more robust and reusable.

// Violation: Invoice handles both business logic AND printing
// Fix: Separate concerns
class Invoice        { double calculate() { ... } }
class InvoicePrinter { void print(Invoice i) { ... } }
class InvoiceDB      { void save(Invoice i)  { ... } }

O — Open/Closed Principle (OCP)

Software entities should be open for extension but closed for modification. Use abstraction (interfaces/abstract classes) to add new behaviour without changing existing code.

interface Shape { double area(); }
class Circle    implements Shape { public double area() { return Math.PI * r * r; } }
class Rectangle implements Shape { public double area() { return w * h; } }
// Adding a new shape requires no change to existing code

L — Liskov Substitution Principle (LSP)

Objects of a subclass should be substitutable for objects of the superclass without altering program correctness. Subclasses must honour the contract of the parent class.

// Violation: Square overrides setWidth() in a way that breaks Rectangle contract
// Fix: Don't force Square to extend Rectangle if their contracts differ
// OR make both implement a Shape interface independently

I — Interface Segregation Principle (ISP)

A client should not be forced to depend on interfaces it does not use. Split large interfaces into smaller, more specific ones.

// Violation: one fat interface Worker with work() + eat() + sleep()
// Fix: separate interfaces
interface Workable  { void work(); }
interface Eatable   { void eat(); }
class Robot implements Workable       { public void work() {} }
class Human implements Workable, Eatable { ... }

D — Dependency Inversion Principle (DIP)

High-level modules should not depend on low-level modules; both should depend on abstractions. Abstractions should not depend on details; details should depend on abstractions.

// Violation: Service directly creates MySQLDatabase instance
// Fix: inject the abstraction
interface Database { void save(String data); }
class MySQLDatabase implements Database { ... }
class Service {
    private Database db; // depends on abstraction
    Service(Database db) { this.db = db; }
}
22 Explain the Liskov Substitution Principle using an example of violation and its correction.
SOLID

LSP (introduced by Barbara Liskov in 1987) states: "If S is a subtype of T, then objects of type T may be replaced with objects of type S without altering the correctness of the program."

Classic Violation — Square extends Rectangle

class Rectangle {
    int width, height;
    void setWidth(int w)  { this.width = w; }
    void setHeight(int h) { this.height = h; }
    int area() { return width * height; }
}
class Square extends Rectangle {
    @Override void setWidth(int s)  { width = height = s; } // changes both!
    @Override void setHeight(int s) { width = height = s; }
}
// LSP test:
Rectangle r = new Square();
r.setWidth(5);
r.setHeight(4);
// Expected area: 20, Actual: 16 — VIOLATED!

Correction

Both Rectangle and Square should implement a common Shape interface independently rather than forcing Square to inherit from Rectangle:

interface Shape { int area(); }
class Rectangle implements Shape {
    int w, h;
    Rectangle(int w, int h) { this.w = w; this.h = h; }
    public int area() { return w * h; }
}
class Square implements Shape {
    int side;
    Square(int s) { this.side = s; }
    public int area() { return side * side; }
}
23 State the Interface Segregation Principle with problem and solution using an example.
SOLID

ISP: Clients should not be forced to depend on interfaces they do not use. Many client-specific interfaces are better than one general-purpose interface.

Problem (Fat Interface)

interface Worker {
    void work();
    void eat();
    void sleep();
}
class Robot implements Worker {
    public void work()  { ... }
    public void eat()   { throw new UnsupportedOperationException(); } // forced!
    public void sleep() { throw new UnsupportedOperationException(); }
}

Solution (Segregated Interfaces)

interface Workable  { void work(); }
interface Eatable   { void eat(); }
interface Sleepable { void sleep(); }

class Robot implements Workable { public void work() { ... } }
class Human implements Workable, Eatable, Sleepable { ... }

Now Robot only implements what it actually does. No forced unused methods.

24 Explain the Open-Closed Principle (OCP) with an example.
SOLID

Proposed by Bertrand Meyer. Software entities (classes, modules, functions) should be open for extension (new behaviour can be added) but closed for modification (existing code is not changed).

Violation

class AreaCalculator {
    double calculate(Object shape) {
        if (shape instanceof Circle) { ... }
        else if (shape instanceof Rectangle) { ... }
        // Adding a Triangle requires MODIFYING this class
    }
}

Correct Design

interface Shape { double area(); }
class Circle    implements Shape { public double area() { return Math.PI*r*r; } }
class Rectangle implements Shape { public double area() { return w*h; } }
class Triangle  implements Shape { public double area() { return 0.5*b*h; } }

class AreaCalculator {
    double calculate(Shape shape) { return shape.area(); } // closed for modification
}

Adding a new shape only requires creating a new class — no modification to AreaCalculator.

25 Describe the Dependency Inversion Principle (DIP) with an example.
SOLID

DIP has two rules: (1) High-level modules should not depend on low-level modules — both should depend on abstractions. (2) Abstractions should not depend on details — details should depend on abstractions. Violating DIP results in tight coupling.

// VIOLATION — tight coupling
class EmailNotifier {
    void send(String msg) { System.out.println("Email: " + msg); }
}
class OrderService {

26 Explain the MVC (Model-View-Controller) Architecture Pattern with a flow diagram.
Architecture

Components

  • Model: Represents the application's data and business logic. Independent of the UI. Notifies the View when data changes.
  • View: Renders the UI based on Model data. Multiple views can represent the same data in different formats. Sends user input to the Controller.
  • Controller: Acts as an intermediary. Receives user actions from the View, processes them (possibly updating the Model), and selects which View to display.

Flow

User Action → [View] → [Controller] → updates [Model]
[Model] → notifies → [View] → renders updated UI to User

1. User interacts with the View (button click)
2. View notifies the Controller
3. Controller processes input, calls Model methods
4. Model updates its state
5. Model notifies View of changes
6. View queries Model and re-renders

Benefits

  • Separation of concerns — UI logic separated from business logic.
  • Multiple views for same data (e.g., table vs chart).
  • Easier to test each component independently.
27 What are Design Patterns? What are the different types? State pros and cons.
Design Patterns

A design pattern is a reusable, named solution to a commonly occurring problem in a given software design context. Introduced by the "Gang of Four" (Gamma, Helm, Johnson, Vlissides) in their classic book. A pattern has: name, problem, solution, and consequences.

Three Categories (by GoF)

  • Creational: Deal with object creation — Singleton, Factory Method, Abstract Factory, Builder, Prototype.
  • Structural: Deal with class/object composition — Adapter, Facade, Proxy, Decorator, Composite, Bridge, Flyweight.
  • Behavioral: Deal with communication between objects — Chain of Responsibility, Command, Iterator, Observer, Strategy, Template Method.

Pros

  • Provide tested, proven solutions to common problems.
  • Establish a common vocabulary for design communication.
  • Improve code reusability, flexibility, and maintainability.
  • Speed up the development process for experienced developers.

Cons

  • Can be over-used — applying a pattern where a simpler solution exists adds unnecessary complexity.
  • Require learning investment to recognise which pattern fits a problem.
  • Can make code harder to understand for developers unfamiliar with patterns.
28 Explain the Singleton Pattern — intent, implementation, and benefits. How do you make a class singleton?
Creational

Intent

Ensure a class has only one instance and provide a global access point to it. Example: a configuration manager, a logging service, a connection pool.

How to Implement Singleton in Java

  1. Make the constructor private to prevent direct instantiation.
  2. Declare a private static field to hold the single instance.
  3. Provide a public static method (getInstance()) that creates the instance lazily on first call and returns the existing one on subsequent calls.
class Singleton {
    private static Singleton obj; // one instance

    private Singleton() {} // prevent external creation

    public static Singleton getInstance() {
        if (obj == null) {
            obj = new Singleton(); // created only once
        }
        return obj;
    }
}

Thread-Safe Singleton

public static synchronized Singleton getInstance() {
    if (obj == null) obj = new Singleton();
    return obj;
}

Benefits

  • Controlled access to the sole instance.
  • Reduced name space (improvement over global variables).
  • Permits refinement via subclassing.
  • The Singleton object is initialized only when first requested (lazy initialization).
29 Describe the Factory Method Pattern with an example, UML structure, and code snippet.
Creational

Intent

Define an interface for creating an object, but let subclasses decide which class to instantiate. Factory Method defers instantiation to subclasses. Also known as Virtual Constructor.

UML Participants

  • Creator (abstract): Declares the factory method (createProduct()). May also define a default implementation.
  • ConcreteCreator: Overrides the factory method to return a specific product.
  • Product (interface/abstract): Defines the interface of objects created.
  • ConcreteProduct: Implements the Product interface.
// Product interface
interface Notification {
    void notifyUser();
}
// Concrete Products
class EmailNotification implements Notification {
    public void notifyUser() { System.out.println("Email sent"); }
}
class SMSNotification implements Notification {
    public void notifyUser() { System.out.println("SMS sent"); }
}
// Creator
abstract class NotificationFactory {
    abstract Notification createNotification(); // factory method
    void send() { createNotification().notifyUser(); }
}
// Concrete Creators
class EmailFactory extends NotificationFactory {
    Notification createNotification() { return new EmailNotification(); }
}
class SMSFactory extends NotificationFactory {
    Notification createNotification() { return new SMSNotification(); }
}
// Client
NotificationFactory f = new EmailFactory();
f.send(); // Output: Email sent

When to Use

When a class cannot anticipate the class of objects it must create, or when subclasses should decide which objects to create. More flexible than direct new calls.

30 Describe the Builder Pattern — intent, structure, and when to use it. State difference from Factory.
Creational

Intent

Separate the construction of a complex object from its representation, allowing the same construction process to create different representations step by step.

Participants

  • Builder (interface): Declares construction steps (buildPart() methods).
  • ConcreteBuilder: Provides specific implementations of construction steps and tracks the product being built.
  • Director: Orchestrates the build steps using the Builder interface.
  • Product: The complex object being constructed.
class BurgerBuilder {
    private String bun, patty, sauce;
    BurgerBuilder setBun(String b)    { this.bun=b;    return this; }
    BurgerBuilder setPatty(String p)  { this.patty=p;  return this; }
    BurgerBuilder setSauce(String s)  { this.sauce=s;  return this; }
    Burger build() { return new Burger(bun, patty, sauce); }
}
// Client
Burger b = new BurgerBuilder().setBun("Sesame").setPatty("Beef").setSauce("Ketchup").build();

Builder vs Factory Method

  • Factory Method creates objects in one step; Builder constructs complex objects step by step.
  • Abstract Factory returns the product immediately; Builder lets you run extra construction steps before fetching the product.
  • Use Builder when an object needs many optional parameters or complex initialization logic.

31 Briefly describe the Adapter Structural Design Pattern — intent, problem, solution, structure, and example.
Structural

Intent

Convert the interface of a class into another interface that clients expect. Adapter lets classes work together that couldn't otherwise because of incompatible interfaces. Also known as Wrapper.

Participants

  • Target: The interface the client expects.
  • Adaptee: The existing class with the incompatible interface.
  • Adapter: Wraps the Adaptee, implementing the Target interface by translating calls.
  • Client: Collaborates with objects through the Target interface.

MediaPlayer Adapter Example (from exam)

// Target
interface MediaPlayer { void play(String type, String file); }
// Adaptee
interface AdvancedMediaPlayer { void playVLC(String f); void playMP4(String f); }
class VLCPlayer implements AdvancedMediaPlayer { void playVLC(String f) {...} void playMP4(String f){} }
// Adapter
class MediaAdapter implements MediaPlayer {
    AdvancedMediaPlayer player;
    MediaAdapter(String type) {
        if(type.equals("vlc")) player = new VLCPlayer();
    }
    public void play(String type, String file) {
        if(type.equals("vlc")) player.playVLC(file);
    }
}
// AudioPlayer uses Adapter to support new formats
class AudioPlayer implements MediaPlayer {
    MediaAdapter adapter;
    public void play(String type, String file) {
        if(type.equals("mp3")) System.out.println("Playing MP3: " + file);
        else { adapter = new MediaAdapter(type); adapter.play(type, file); }
    }
}

Object Adapter vs Class Adapter

  • Object Adapter (composition): Adapter holds a reference to the Adaptee instance. More flexible — can work with Adaptee subclasses.
  • Class Adapter (inheritance): Adapter inherits from both Target and Adaptee. Only possible in languages that support multiple inheritance (not Java).
32 Describe the Proxy Design Pattern — intent, three main variations, and an example.
Structural

Intent

Provide a surrogate or placeholder for another object to control access to it. The Proxy implements the same interface as the real object but intercepts calls, adding additional behavior (access control, lazy loading, caching).

Three Variations

  • Virtual Proxy (Lazy Initialization): Defers the creation of an expensive real object until it is actually needed. Example: loading high-resolution images only when displayed.
  • Protection Proxy (Access Control): Controls access to the real object based on permissions. Example: a proxy that checks user roles before allowing database operations.
  • Remote Proxy: Provides a local representative for an object in a different address space. Example: Java RMI stubs.
  • Cache Proxy: Caches results of expensive operations and returns cached responses for repeated requests.

Song Library Example (from exam)

interface Song { void play(); String getTitle(); }

class RealSong implements Song {    // heavy object — fetches media stream
    private String title, artist, stream;
    RealSong(String title) {
        this.title = title;
        this.stream = "...fetch from DB..."; // expensive
    }
    public void play()        { System.out.println("Playing: " + stream); }
    public String getTitle()  { return title; }
}
class SongProxy implements Song {   // shown in listing, lazy loads stream
    private RealSong real;
    private String title;
    SongProxy(String title) { this.title = title; }
    public String getTitle() { return title; } // cheap
    public void play() {
        if (real == null) real = new RealSong(title); // load only on play
        real.play();
    }
}

This is a Virtual Proxy pattern — ideal for the use-case described in the exam (display only title/artist in the list; load full media stream only when the song is selected).

33 Describe the Chain of Responsibility behavioral pattern — intent, structure, and benefits. Include a Logging System example.
Behavioral

Intent

Avoid coupling the sender of a request to its receiver by giving more than one object a chance to handle the request. Chain the receiving objects and pass the request along the chain until an object handles it.

Participants

  • Handler (abstract): Defines the interface for handling requests and holds a reference to the next handler in the chain.
  • ConcreteHandler: Handles requests it is responsible for; otherwise forwards to the successor.
  • Client: Initiates the request to the first handler in the chain.

Logging System Example (from exam)

abstract class Logger {
    static final int INFO = 1, ERROR = 2, DEBUG = 3;
    protected int level;
    protected Logger next;
    void setNext(Logger next) { this.next = next; }
    void log(int level, String msg) {
        if (this.level <= level) write(msg);
        if (next != null) next.log(level, msg);
    }
    protected abstract void write(String msg);
}
class ConsoleLogger extends Logger {
    ConsoleLogger(int level) { this.level = level; }
    protected void write(String msg) { System.out.println("Console: " + msg); }
}
class ErrorLogger extends Logger {
    ErrorLogger(int level) { this.level = level; }
    protected void write(String msg) { System.err.println("Error log: " + msg); }
}
// Build chain: console -> error -> debug
ConsoleLogger c = new ConsoleLogger(Logger.INFO);
ErrorLogger   e = new ErrorLogger(Logger.ERROR);
c.setNext(e); // chain
c.log(Logger.INFO, "System started"); // handled by ConsoleLogger

Benefits

  • Reduced coupling between sender and receiver.
  • Flexible assignment of responsibilities — chain can be changed at runtime.
  • New handlers can be added without changing existing code.
34 Describe the Façade Pattern — intent, when to use, and example.
Structural

Intent

Provide a simplified, unified interface to a complex subsystem. The Façade hides the complexity of the subsystem from clients while still allowing advanced users to access the subsystem directly if needed.

Structure

  • Façade: Knows which subsystem classes handle a request; delegates client requests to the appropriate subsystem objects.
  • Subsystem classes: Implement subsystem functionality; have no knowledge of the façade.
  • Client: Communicates with the subsystem through the façade.
// Complex subsystem
class CPU        { void start()    {} }
class Memory     { void load()     {} }
class HardDrive  { void read()     {} }

// Façade
class ComputerFacade {
    private CPU cpu = new CPU();
    private Memory mem = new Memory();
    private HardDrive hdd = new HardDrive();
    void startComputer() { cpu.start(); mem.load(); hdd.read(); }
}
// Client only calls facade
ComputerFacade pc = new ComputerFacade();
pc.startComputer(); // hides subsystem complexity

Benefits

  • Shields clients from complex subsystem components.
  • Promotes loose coupling between clients and the subsystem.
  • Doesn't prevent clients from using subsystem classes directly when needed.
35 Describe the structure of the Iterator Pattern.
Behavioral

Intent

Provide a way to sequentially access elements of a collection (aggregate object) without exposing its underlying representation.

Participants

  • Iterator (interface): Defines the traversal interface: hasNext(), next(), optionally remove().
  • ConcreteIterator: Implements the Iterator interface, tracking the current position in the traversal.
  • Aggregate (interface): Defines method to create an Iterator (createIterator()).
  • ConcreteAggregate: Implements the Aggregate interface, returning an instance of the appropriate ConcreteIterator.
interface Iterator<T> { boolean hasNext(); T next(); }
class NumberCollection {
    private int[] nums;
    NumberCollection(int[] n) { this.nums = n; }
    Iterator<Integer> iterator() {
        return new Iterator<Integer>() {
            int i = 0;
            public boolean hasNext() { return i < nums.length; }
            public Integer next()    { return nums[i++]; }
        };
    }
}

Benefits

  • Supports multiple simultaneous traversals.
  • Simplifies the aggregate interface — traversal logic is moved to the Iterator.
  • Supports different traversal strategies without changing the aggregate.
36 What is an Anti-pattern? Differentiate between a Pattern and an Anti-pattern.
Anti-Patterns

What is an Anti-Pattern?

An anti-pattern is a commonly used but counterproductive solution to a recurring problem — it appears to be a good idea but typically produces negative results (technical debt, maintenance problems, poor performance). Unlike design patterns, anti-patterns document bad practice and provide a refactored solution (how to escape the anti-pattern).

Pattern vs Anti-Pattern

  • Design Pattern: A proven, reusable solution that results in better software quality. Examples: Singleton, Factory, Observer.
  • Anti-Pattern: A frequently used poor solution that typically makes things worse. Examples: The Blob, Lava Flow, Vendor Lock-In, Analysis Paralysis.
  • Anti-patterns include: A description of the problem, the bad solution (anti-pattern itself), consequences/symptoms, typical causes, and the refactored solution (how to fix it).

Why Study Anti-Patterns?

  • Provide easily identifiable templates for common problems and their fixes.
  • Real-world experience in recognising recurring design mistakes.
  • Common vocabulary for discussing and resolving problems.
  • Ensure common mistakes are not repeated within an organization.
37 Describe the Blob (God Object) Anti-pattern — symptoms, causes, and refactored solution.
Anti-Patterns

What is the Blob?

A Blob is found in procedural-style designs where one class monopolizes the processing while most other classes only hold data or execute simple processes. The single complex controller class surrounded by simple data classes violates high cohesion.

Symptoms & Consequences

  • A single class with a large number of attributes and operations (60+ usually indicates Blob).
  • A disparate collection of unrelated attributes and operations — overall lack of cohesion.
  • The Blob class is too complex for reuse and testing.
  • May be expensive to load into memory, using excessive resources even for simple operations.

Typical Causes

  • Lack of object-oriented architecture (procedural mindset applied to OO code).
  • Lack of any architecture or architecture enforcement.
  • Too limited design review (problems not caught early).

Refactored Solution (3 Steps)

  1. Categorize: Identify and group related attributes and operations by cohesive contracts/responsibilities.
  2. Migrate: Find "natural homes" for each contract-based group and move them to appropriate classes. (e.g., catalog-related operations from LIBRARY class move to CATALOG class.)
  3. Remove redundancies: Remove "far-coupled" or redundant indirect associations. Migrate associations to derived classes at the appropriate base class level. Replace transient associations with type specifiers.
38 Describe the Analysis Paralysis Anti-pattern — symptoms and typical causes.
Anti-Patterns

What is Analysis Paralysis?

A project management anti-pattern where an over-emphasis on analysis prevents actual progress, creating an unproductive cycle of repeated analysis and model rework without moving to design or implementation.

Symptoms & Consequences

  • Multiple project restarts and much model rework, due to personnel changes or project direction changes.
  • Design and implementation issues are continually reintroduced in the analysis phase.
  • Cost of analysis exceeds expectation without a predictable end point.
  • The analysis phase no longer involves user interaction — much analysis is speculative.
  • Complexity of analysis models results in intricate implementations, making the system difficult to develop, document, and test.

Typical Causes

  • Management assumes a strict waterfall progression; insists on completing all analysis before design begins.
  • Management has more confidence in analyzing than in designing and implementing.
  • Goals in the analysis phase are not well defined.
  • Management is unwilling to make firm decisions when parts of the domain are sufficiently described.
  • Project vision and focus on the deliverable is diffused — analysis goes beyond providing meaningful value.

Refactored Solution

Adopt incremental development. Use internal increments (infrastructure, data access) and external increments (user-visible functionality) to build the system progressively, learning details of the problem as you go rather than assuming full upfront knowledge.

39 Describe the Vendor Lock-In Anti-pattern — symptoms, causes, and refactored solution.
Anti-Patterns

What is Vendor Lock-In?

A software project becomes completely dependent on a specific vendor's technology. When vendor upgrades occur, software changes and interoperability problems result in continuous maintenance. Expected features are delayed, causing schedule slips.

Symptoms & Consequences

  • Commercial product upgrades drive the entire application maintenance cycle.
  • Promised product features are delayed or never delivered.
  • The product varies significantly from advertised open standards.
  • Missing a product upgrade entirely may require full product repurchase and reintegration.

Typical Causes

  • Product selected based entirely on marketing/sales information, not technical inspection.
  • No technical approach for isolating application software from direct vendor dependency.
  • Application programming requires in-depth product-specific knowledge.
  • Complexity of product technology exceeds application needs.

Refactored Solution — Isolation Layer

Introduce an isolation layer that separates the application from vendor-specific details. The application interacts only with the isolation layer's abstract API; the isolation layer maps those calls to vendor-specific implementations. Benefits:

  • Changing the underlying vendor requires only changing the isolation layer, not the entire application.
  • Supports multiple concurrent infrastructures.
  • Provides a more convenient programming interface at the right level of abstraction.
40 Describe the Lava Flow Anti-pattern.
Anti-Patterns

What is Lava Flow?

Lava Flow describes the presence of dead code, unused or barely-used classes, and unnecessary complexity that remain in a system because developers are afraid to remove them — unsure if something depends on them. Like lava that solidifies into immovable rock, this code "hardens" in place.

Symptoms

  • Large sections of commented-out code with no clear explanation.
  • Unused variables, undocumented classes, and dead methods lingering in the codebase.
  • Developers say "I'm not sure what that class does, but don't touch it — it might break something."
  • Inconsistent design approaches across the codebase due to evolved-but-unclean development.

Typical Causes

  • Rapid prototyping code that was promoted to production without cleanup.
  • Single developer who wrote critical code but has since left; no documentation.
  • Architectural experiments that were abandoned but not removed.

Refactored Solution

Conduct systematic code reviews and use refactoring tools to identify and safely remove dead code. Establish clear documentation and architecture standards from the start of development. Use automated tests to gain confidence before removing suspect code.

41 A pizza store design has issues — identify violations and suggest corrections. (Design principle application)
SOLID

Common Violations in a Pizza Store Design

A typical problematic pizza store design often violates OCP and DIP by having a single class (e.g., PizzaStore) with large if/else or switch blocks for each pizza type.

Identified Violations

  • OCP Violation: Adding a new pizza type requires modifying the existing PizzaStore class.
  • SRP Violation: A single class handles both ordering logic AND pizza creation.
  • DIP Violation: High-level ordering logic directly depends on low-level concrete pizza classes.

Corrected Design (using Factory Method + OCP)

abstract class Pizza { abstract void prepare(); abstract void bake(); }
class CheesePizza extends Pizza { ... }
class PepperoniPizza extends Pizza { ... }

abstract class PizzaStore {
    abstract Pizza createPizza(String type); // factory method
    final Pizza orderPizza(String type) {
        Pizza p = createPizza(type); // delegate creation to subclass
        p.prepare(); p.bake(); return p;
    }
}
class NYPizzaStore extends PizzaStore {
    Pizza createPizza(String type) {
        if(type.equals("cheese")) return new CheesePizza();
        return new PepperoniPizza();
    }
}

Adding a new pizza type now only requires creating a new subclass of Pizza — no modification to existing code.

45 Describe the approaches for identifying classes (Noun Phrase, Common Class Patterns, CRC, Use Case Driven).
OO Analysis

1. Noun Phrase Approach

Read the requirements document and identify all nouns and noun phrases. Treat nouns as candidate classes and verbs as methods. Classify nouns into: Relevant (core domain concepts), Fuzzy (might become attributes or enums), and Irrelevant (outside scope, UI elements). Remove duplicates, attributes masquerading as classes, and vague/overly-specific nouns.

2. Common Class Patterns Approach

Use recurring patterns for class types (Shlaer & Mellor):

  • Concept class: Intangible business concepts — Account, Customer.
  • Event class: Time-stamped occurrences — Transaction, Withdrawal.
  • Organization class: Group of people/resources — Bank, Branch.
  • People class: Roles users play — Clerk, Beneficiary.
  • Place class: Physical locations — Branch, Office.
  • Tangible things/devices: Physical objects — Sensor, Terminal.

3. CRC Cards (Class, Responsibility, Collaborators)

Index cards listing: class name, responsibilities (what it knows/does), and collaborating classes. Used in brainstorming sessions; helps identify interactions and assign responsibilities early.

4. Use Case Driven Approach

Analyse use cases — actors and use-case descriptions contain candidate classes. Nouns that appear in use-case flows are candidate classes; verbs become operations. Combined with the noun-phrase approach for completeness.

46 Identify SOLID principles violated in a given design and suggest corrections.
SOLID

Typical Violations to Look For

  • SRP violation: A class handling multiple unrelated concerns (e.g., data storage + business logic + UI rendering in one class). Fix: Split into separate classes each with a single responsibility.
  • OCP violation: Existing code must be modified every time new behaviour is added (e.g., if/else type checks). Fix: Use polymorphism — abstract class/interface with subclasses per behaviour.
  • LSP violation: A subclass overrides methods in a way that breaks the parent class contract, or throws exceptions for methods it doesn't support. Fix: Rethink inheritance hierarchy; use interfaces instead of deep inheritance.
  • ISP violation: A large interface forces implementing classes to provide stub implementations for methods they don't use. Fix: Split the interface into smaller, role-specific interfaces.

48 Is the statement Object o = new ArrayList<String>(); valid in Java? Justify.
Java

Yes, this statement is valid in Java.

In Java, every class ultimately extends Object. ArrayList<String> extends AbstractList which extends AbstractCollection which implements Collection which extends Iterable — and all of these ultimately inherit from Object.

Therefore, ArrayList<String> IS-A Object. This is a case of upcasting — storing a more specific type in a variable of a more general type. This is allowed in Java (and is the basis of polymorphism).

Object o = new ArrayList<String>(); // valid — upcasting
// However, to use ArrayList-specific methods, you'd need to downcast:
((ArrayList<String>) o).add("Hello");
Note: While valid, this is generally bad practice as it loses type information. Prefer List<String> list = new ArrayList<>(); for programming to an interface.

Common GRASP Violations

  • Violation of Information Expert: Assigning the responsibility to compute a total to a class that doesn't have the required data (e.g., assigning calculateTotal() to Register when only Sale has SalesLineItems). Fix: Assign to Sale which has all the line items.
  • Violation of Creator: Having a class create objects it has no logical connection to. Fix: Let Sale create SalesLineItem since it aggregates them.
  • Low Cohesion violation (Bloated class): A single class with many unrelated methods — similar to the Blob anti-pattern. Fix: Refactor into multiple focused classes.
  • High Coupling violation: A class depending on many other classes directly. Fix: Use indirection/intermediary, dependency injection, or program to interfaces.

Information Expert — Fix Example (from exam: Test marks)

If a Test consists of multiple Question objects each with a marks attribute, then responsibility to compute total marks should be assigned to Test, because Test is the Information Expert — it aggregates all Question objects and has access to their marks.

class Question { int marks; }
class Test {
    List<Question> questions;
    // Information Expert: Test computes its own total
    int computeTotalMarks() {
        return questions.stream().mapToInt(q -> q.marks).sum();
    }
}
51 Specify when to use the Builder Pattern and state the difference between Factory Method and Abstract Factory.
Creational

When to Use Builder

  • When an object requires many optional parameters or configurations (avoids telescoping constructors).
  • When construction involves multiple steps that should be executed in a specific order.
  • When the same construction process should produce different representations of an object (e.g., building a house in stone vs wood).

Factory Method vs Abstract Factory

  • Factory Method: Creates one product. Defines a method in a creator class that subclasses override to produce specific products. Focus: one type of object, deferred to subclasses.
  • Abstract Factory: Creates families of related objects without specifying their concrete classes. Provides multiple factory methods for different product types in a family. Focus: ensuring compatibility among related products.
  • Example: Factory Method: createButton() in a UI framework. Abstract Factory: createButton() + createTextBox() + createCheckbox() all in a WindowsUIFactory that ensures consistent Windows-style UI components.
52 Describe the essential elements of a Design Pattern and identify the essential elements (Name, Problem, Solution, Consequences).
Design Patterns

According to the Gang of Four, a design pattern has four essential elements:

  • Pattern Name: A handle used to describe the design problem, its solution, and consequences in a word or two. Building a vocabulary of patterns (e.g., "Singleton", "Observer") aids communication.
  • Problem: Describes when to apply the pattern — the context and the problem it solves. May describe specific design problems such as how to represent algorithms as objects, or conditions that must exist before the pattern makes sense.
  • Solution: Describes the elements that make up the design — their relationships, responsibilities, and collaborations. The solution is described abstractly, not as a specific concrete design or implementation.
  • Consequences: The results, trade-offs, and costs of applying the pattern. Includes space and time trade-offs, language and implementation issues, and impact on system flexibility, extensibility, or portability.
