1. SDD Recap

Syntax Directed Definition (SDD): Grammar + semantic rules. Each grammar symbol has attributes; each production has rules to compute attribute values.

AttributeComputed fromTraversal
SynthesizedChildren's attributes (flows UP)Post-order (bottom-up)
InheritedParent + left siblings (flows DOWN/ACROSS)Pre-order (top-down)

How Attribute Values Flow

  1. First compute any base values already known at leaves like num.lexval or int.
  2. Pass inherited attributes from the parent or left sibling before visiting the next symbol.
  3. Evaluate the child subtree once those inherited values are available.
  4. Bring synthesized attributes back upward to the parent.
  5. Repeat until the left-hand side non-terminal gets its final value.
// Quick flow example for D → T L
T.type = integer
T.width = 4
L.inhType = T.type
L.inhWidth = T.width
update(id.entry, L.inhType, L.inhWidth)

An SDD with only synthesized attributes = S-attributed SDD.

Every S-attributed SDD is also L-attributed. S-attributed → post-order traversal. Inherited → pre-order.

2. L-Attributed SDD

An SDD is L-attributed if each inherited attribute of Xj in production A → X1 X2 … Xn depends only on:

  1. Attributes of symbols to the LEFT of Xj (i.e., X1 … Xj-1) — this is what "L" stands for
  2. The inherited attributes of A (the parent)
Theorem: Inherited attributes in L-attributed SDDs can be computed by a Pre-Order (depth-first, left-to-right) traversal of the parse tree.
L-attributed allows natural left-to-right evaluation. Every S-attributed is also L-attributed. L-attributed → pre-order traversal.

6. Syntax Directed Translation (SDT)

SDT vs SDD: SDT = more implementation-oriented; semantic actions {} are embedded inside the RHS of productions indicating when they execute.

  • Yacc uses Translation Schemes (SDTs)
  • For synthesized attributes: action goes at end of production
  • For inherited attributes: action goes before the symbol it computes for
  • Postfix SDT: All actions at end of production — works with bottom-up parsers

Problematic SDT — Infix to Prefix

E → {printf("+");} E + T  // action BEFORE E → prefix
E → T
T → {printf("*");} T * F
T → F
F → (E)
F → digit {printf(digit.lexval);}

Implementation: Build parse tree, add actions as children, do pre-order traversal, execute action when visited.

Postfix SDT — Desk Calculator

E → E₁ + T  { stack[top-2].val = stack[top-2].val + stack[top].val; top = top-2; }
T → T₁ * F  { stack[top-2].val = stack[top-2].val * stack[top].val; top = top-2; }
F → (E)     { stack[top-2].val = stack[top-1].val; top = top-2; }
Postfix SDT → actions at end → bottom-up parser. Problematic SDT → action in middle → use preorder traversal of parse tree with embedded action nodes.

7. L-Attributed SDD → SDT Conversion

Rule:

  • Place computation of inherited attributes BEFORE the non-terminal in RHS
  • Place computation of synthesized attributes at END of production

Example: Multiplication grammar

SDD ProductionSDT (Translation Scheme)
T → F T' (T'.inh = F.syn; T.syn = T'.syn)T → F {T'.inh = F.syn;} T' {T.syn = T'.syn}
T' → *F T'₁ (T'₁.inh = T'.inh * F.syn; T'.syn = T'₁.syn)T' → *F {T'₁.inh = T'.inh * F.syn;} T'₁ {T'.syn = T'₁.syn}
T' → ε (T'.syn = T'.inh)T' → ε {T'.syn = T'.inh;}
F → digit (F.syn = digit.lexval)F → digit {F.syn = digit.lexval;}

L-Attributed SDD to SDT — During LR Parsing (Marker Non-terminal)

Introduce Marker Non-terminal M for each embedded action:

// Original:
A → α {a} β
// Converted (marker M):
A → α M β
M → ε {a}   // action happens when M is reduced

Example — while statement:

S → while ( M C ) N S₁
M → ε  { L1=newLabel(); L2=newLabel(); C.true=L2; C.false=S.next; }
N → ε  { S₁.next = L1; }
// Final: S.code = L1 || C.code || L2 || S1.code

8. Intermediate Code Generation — IC, DAG

What is Intermediate Code?

Code between high-level source and machine code. Input from semantic analyser (annotated syntax tree). Output feeds into code optimization and generation.

Key advantage: Write N front-ends + 1 optimizer + M back-ends instead of N×M full compilers. Machine-independent optimization possible = retargeting.

Types of Intermediate Representation

LevelExamplesBest for
High-level (close to source)Syntax trees, DAG, Java BytecodeMachine-independent optimization
Low-level (close to machine)Three Address Code (TAC), SSAMachine-dependent optimization, register allocation
ClassificationExamples
Language-specificJava Bytecode, P-code for Pascal
Language-independentThree-address code
GraphicalSyntax trees, DAGs
LinearTAC, SSA

DAG — Directed Acyclic Graph

Like a syntax tree but common subexpressions are shared (single node, multiple parents). Reduces redundant computation.

  • SDD to build DAG: same as syntax tree but CHECK if identical node exists → RETURN existing node, else CREATE new node
  • Applications: CSE identification, identify inputs from outside block, identify outputs used outside block
DAG vs Syntax tree: DAG shares common subexpressions → fewer nodes. Building DAG is costlier due to equality check overhead.

DAG Example: ((x+y) - ((x+y)*(x-y))) + ((x+y)*(x-y))

11. Static Single Assignment (SSA)

Each variable assigned exactly once. Multiple versions of a variable: x₁, x₂, x₃… widely used by modern optimising compilers (GCC, LLVM, HotSpot).

φ-function

At merge points (where control flow joins), use φ(a₁, a₂, …) to select value based on which control path was taken. Number of arguments = number of incoming edges.

Example — while loop

// Original:
x = 0;  y = 0;
while (x < 10) { y = y+x; x = x+1; }
print(y);

// SSA Form:
x₁ = 0;  y₁ = 0;
x₂ = φ(x₁, x₃)   // from init OR from loop body
y₂ = φ(y₁, y₃)
(x₂ < 10)?
  y₃ = y₂ + x₂
  x₃ = x₂ + 1
print(y₂)
SSA: each variable defined once. φ-function at merge points. # args to φ = # incoming edges. Used by GCC, LLVM, HotSpot.

12. CFG & Basic Blocks

Basic Blocks

Maximal sequence of consecutive instructions with: control can enter ONLY at FIRST instruction, control leaves ONLY at LAST instruction.

Rules to Find Leaders (basic block boundaries)

  1. The first instruction of the program is a leader
  2. Any instruction that is the target of a conditional or unconditional jump is a leader
  3. Any instruction that immediately follows a conditional or unconditional jump is a leader

Each basic block = leader instruction + all instructions up to (but not including) next leader.

CFG Construction Rules

  • Nodes = basic blocks + ENTRY + EXIT
  • Edge from B1 → B2 if B2 immediately follows B1 in code OR B1 ends with jump to B2
  • ENTRY has edge to first block; EXIT has edge from last block

CFG Example (17-instruction array init)

Basic Block: sequential, no branching. Leaders: first instr, target of jump, instr after jump. CFG nodes = basic blocks. ENTRY/EXIT nodes added.

14. Constant Folding & Propagation

Constant Folding

Evaluate constant expressions at compile time rather than at runtime.

// Before:
i = 30 * 20 * 10        // → i = 6000 (done at compile time)
x = 5 + 4 / 2           // → x = 7
s = "dog" + "house"     // → s = "doghouse"
0 * x = 0               // even without knowing x!
1 * x = x               // algebraic identity

Constant Propagation

Substitute known constant values wherever the variable is used.

// Original:
int a = 10; int b = 45 - a/2; return b * (200/a + 2);

// Propagate a=10:
int b = 45 - 10/2; return b * (200/10 + 2);

// Fold b = 45-5 = 40:
int b = 40; return b * (20 + 2);

// Propagate b=40, fold:
return 40 * 22;

// Final (a,b become dead code):
return 880;
Constant Folding = evaluate at compile time. Constant Propagation = substitute known constants. Together: a=10 → propagate → fold → dead code elimination → final answer.

15. CSE, Copy Propagation, Dead Code Elimination

Common Subexpression Elimination (CSE)

If expression E was previously computed and its operands haven't changed, reuse the result instead of recomputing.

// Before:
a = b * c + g;
d = b * c * e;

// After CSE:
t1 = b * c;    // computed once
a = t1 + g;
d = t1 * e;    // reuse t1

Copy Propagation

After a copy statement u = v, use v instead of u wherever u appears.

// Before:
q = b           // copy
r = q * q

// After (propagate q → b):
r = b * b       // q may become dead code

Dead Code Elimination

Remove code that is never executed or whose result is never used.

// Before:
void f() {
  global = 1;   // dead: immediately overwritten
  global = 2;
  return;
  global = 3;   // unreachable
}

// After:
void f() { global = 2; return; }
CSE: rely on data flow analysis. Copy propagation: "use v for u" after u=v. DCE: variable not live after assignment → assignment is dead code.

16. Strength Reduction & Loop Optimizations

Strength Reduction

Replace expensive operations with cheaper equivalents.

ExpensiveCheaper
x ^ 2x * x
x * 2x + x   OR   x << 1
x / 2x >> 1
x / 4x >> 2

Packing Temporaries

If one temporary becomes dead after a statement, the next temporary can reuse the same register or storage slot.

// Before:
t1 = a + a
t2 = t1 + b    // t1 not used after this
c = t2 * t2

// After (t2 reuses t1's register):
t1 = a + a
t1 = t1 + b
c = t1 * t1

Loop Invariant Detection (Code Motion)

If a computation inside a loop yields the same result every iteration, move it outside.

// Before:
while (i <= limit - 2) { ... }

// After (code motion):
t = limit - 2;          // computed ONCE before loop
while (i <= t) { ... }

Loop Unrolling

Duplicate loop body to reduce iterations and branch overhead.

// Before:
for (i = 0; i < 100; i++) g();

// After (unrolled by 2):
for (i = 0; i < 100; i += 2) { g(); g(); }  // 50 iterations instead of 100

Induction Variable Detection

Variable whose value changes by a fixed amount each iteration. Replace multiplication in loop by addition.

// Before:
L: i = i + 1
   t1 = 4 * i        // recomputed every iteration
   t2 = a[t1]
   if t2 < v goto L

// After (induction: t1 increases by 4 each time):
   Initialize: t1 = 4 * i
L: t1 = t1 + 4       // increment by fixed amount instead of multiply
   t2 = a[t1]
   if t2 < v goto L
Loop invariant → code motion (move out). Induction variable → strength reduction (mul→add). Unrolling → reduces branches. Both are loop optimizations.

17. Local Optimization Using DAG

Build a DAG for each basic block. Read optimized code from the DAG. Automatically applies CSE + copy propagation + DCE.

Full Example: Apply all local optimizations

StepOptimizationCode
Original—a=x², b=3, c=x, d=c*c, e=b*2, f=a+d, g=e*f
1Strength Reductiona=x*x (x²→x*x); e=b<<1 (b*2→shift)
2Constant PropagationPropagate b=3: e=3<<1=6; propagate c=x: d=x*x

Final—a=x*x; e=6; f=a+a; g=6*f
Local optimization = one basic block. DAG automates CSE + copy propagation + DCE. Build DAG → read optimized code from it.

Worked Example: when simplification reveals the result

// Original block
a = b + c
b = b - d
c = c + d
e = b + c

// Substitute latest values into e
e = (b - d) + (c + d)

// Simplify
e = b + c

// Conclusion
e computes the same value as the old a

18. Global Optimization on CFG

Apply optimizations across basic blocks using the full CFG.

Steps (exam pattern):

  1. Identify constant conditions → determine unreachable blocks → remove dead blocks (DCE)
  2. Apply constant propagation across blocks
  3. Apply loop invariant code motion
  4. Within each block, construct DAG and optimize (CSE, DCE)
  5. Apply global CSE (same computation in different blocks)
  6. Apply loop optimizations (strength reduction, unrolling)
For exam: given a CFG → apply constant propagation → remove dead blocks → move loop invariants → use DAG per block → global CSE.

Worked CFG Pipeline

// Core idea from the slides
m = 1
limit = 10
i = 0
if m == 1 goto B2
n = 0
...
B2: n = 2
B4: t1 = limit - n
if i < t1 goto B5
B5: x = 2 * m
    i = i + 1
    goto B4
  1. Since m = 1, the jump to B2 is always taken.
  2. The block assigning n = 0 becomes unreachable, so remove it.
  3. Propagate n = 2 into t1 = limit - n.
  4. Fold constants: t1 = 10 - 2 = 8.
  5. Replace the test by if i < 8 goto B5.
  6. If t1 is no longer needed, delete it as dead code.
  7. x = 2 * m is loop-invariant, so move it outside the loop.
// Optimized shape
i = 0

goto exit
body: i = i + 1

19. Next-Use Algorithm

Determines when a variable's value will be used next within a basic block — helps decide register allocation (keep in register until next use; free after last use).

Assumptions: All variables live on exit (stored back to memory). Temporaries are dead on exit.

Two-Pass Algorithm

Pass 1 — Forward scan, initialise symbol table

For every variable X: set X.live = FALSE, X.next_use = NONE

Pass 2 — Backward scan (from last statement)

For each statement (i): x = y op z:

  1. Copy live/next-use info from symbol table into the tuple (instruction record)
  2. Update symbol table: x.live=FALSE, x.next_use=None; y.live=TRUE, y.next_use=i; z.live=TRUE, z.next_use=i

Example: x:=y+z, z:=x*5, y:=z-7, x:=z+y

StmtX.liveX.nextY.liveY.nextZ.liveZ.next
(1) x:=y+zF-T1T1
(2) z:=x*5T2F-F-
(3) y:=z-7F-F-T3
(4) x:=z+yF-T4T4

(The table shows Instruction Info after each statement is processed in Pass 2)

Next-use: 2-pass. Pass 1 initialise to F/NONE. Pass 2 scan BACKWARD. At x=y op z: copy info to tuple, then x.live=F; y.live=T,next=i; z.live=T,next=i.

20. Live Variable Analysis

Variable x is live at point p if its value at p might still be used along some path starting at p. Otherwise it is dead.

Applications: Register allocation (dead var's register can be reused), Dead code elimination (assignment to dead var is useless).

Data Flow Values & Equations

SetDefinition
use[B]Variables used in B before being defined in B
def[B]Variables defined in B before being used in B
in[B]Variables live on ENTRY to B
out[B]Variables live on EXIT from B
OUT[B] = ∪ (IN[S]) for all successors S of B
IN[B] = use[B] ∪ (OUT[B] − def[B])

Algorithm

  1. Initialize all IN[B] = ∅
  2. For each block B (in reverse order), compute use[B] and def[B]
  3. Iterate until no IN/OUT set changes:
      OUT[B] = ∪ IN[successors]
      IN[B] = use[B] ∪ (OUT[B] − def[B])
Liveness: backward analysis. OUT = union of IN of successors. IN = use ∪ (OUT - def). Used for register allocation and DCE.

23. Code Generator Algorithm

Register & Address Descriptors

DescriptorWhat it tracks
Register DescriptorFor each register: which variable(s) currently hold their value in this register
Address DescriptorFor each variable: where its current value can be found (register, memory, or both)

getReg() Algorithm

  1. Return an empty register if available
  2. If y is in register R and R only holds y and y has no next use → return R (y is dead, R is free)
  3. If no free register: find register R holding y, generate ST M, R for every memory location M in y's address descriptor → return R (spilling)
  4. If still no suitable register: operate on memory location

Spilling

When all registers are occupied by live variables, save a register's content to memory (spill) and reuse that register. Spilled value loaded back when needed.

Principle: Check for empty register → check for dead variable → spill (choose register needed furthest in future).

Full Worked Example (3 registers, a and d live on exit)

25. Activation Trees & Records

Activation Tree

Tree showing all procedure calls during ONE run of the program. Root = main(). Each node = one activation (execution) of a procedure.

Procedure calls → preorder traversal  |  Returns → postorder traversal  |  Control flow → depth-first traversal

If a is ancestor of b in the tree: a's lifetime contains b's lifetime (b started after a and finishes before a).

Example — Fibonacci

Activation Record (Stack Frame)

Calling & Return Sequences

Calling Sequence (Caller):

  1. Evaluate actual parameters, store at beginning of callee's AR
  2. Store return address in callee's AR
  3. Store old top-sp in control link; increment top-sp past callee's fixed fields
  4. Jump to callee's code

Return Sequence (Callee):

  1. Place return value next to parameters
  2. Restore top-sp and registers from saved machine status
  3. Branch to return address stored in AR
Activation record fields: Actual params, Return values, Control link, Access link, Saved status, Local data, Temporaries. Control flow = depth-first on activation tree.

26. Access Links & Displays

Nesting Depth

  • Procedures not nested within any other = depth 1 (all C functions are depth 1)
  • If p defined immediately within q at depth i → p is at depth i+1
  • Example (Quicksort ML): sort=1, readarray=2, exchange=2, quicksort=2, partition=3

Access Links

Pointer in each AR pointing to the most recent activation of the immediately surrounding procedure. Used to find nonlocal variables.

To access variable x defined in procedure q (depth nq) from procedure p (depth np): Follow access link chain np - nq times to reach q's AR.

Cases for Setting Access Link

CaseConditionAccess link points to
Case 1np > nq (p deeper than q)p defined inside q → access link = caller's AR (nesting depth just one less)
Case 2np < nq (p shallower)Follow access links from q for (nq - np + 1) hops → reaches r where p is defined
Case 3np == nq (same depth)Access link of p = access link of q

Displays

Array d where d[i] = pointer to highest AR on stack for procedures at nesting depth i. Allows constant-time access to any nonlocal variable (no chain traversal needed).

Access LinksDisplays
Lookup costVariable (chain traversal)Constant time (index into d)
Maintenance costVariableConstant
Access link: follow np-nq times. Displays: d[i] = highest AR at depth i → O(1) access. Access link = static link (not dynamic/control link).

27. Register Allocation by Graph Colouring

Map register allocation to the graph colouring problem.

  1. Liveness Analysis: Determine live ranges of all variables
  2. Build Interference Graph: Each node = variable; edge = two variables are live at same time (interfere → can't share register)
  3. Graph Colouring: Assign colours (registers) to nodes such that no two adjacent nodes have same colour
  4. If k registers available: is the graph k-colourable?
  5. If not k-colourable → spill (store some variable to memory)
Register allocation ≡ graph colouring. k registers = k colours. Adjacent nodes = interfering variables = different colours required. NP-complete in general.
Interference graph: node=variable, edge=live at same time. k-colouring = k registers. Graph colouring is NP-complete → heuristics used in practice.

Code Generator Design Issues

  • Input to code generator: IR + symbol-table information for addresses.
  • Target-program forms: absolute machine code, relocatable machine code, or assembly code.
  • Main criterion: generated code must be correct before it is optimized.
  • Design depends on: the IR, the target machine, and the run-time system.

Instruction Selection

Instruction selection decides how each IR statement is mapped to target instructions. The quality of code depends on:

  1. How low-level the IR already is
  2. How rich or restricted the target ISA is
  3. Whether we want only correct code or efficient code too
Naive statement-by-statement translation is easy, but it often creates redundant loads and stores.

Register Allocation vs Register Assignment

TermMeaning
Register allocationChoose which values should stay in registers at a given point
Register assignmentChoose the exact register number for each selected value

Evaluation order also matters: some computation orders need fewer registers because they keep fewer intermediate results live at once.

Access to Nonlocal Data in Nested Procedures

For nested procedures, the compiler can decide statically where a variable is declared, but at run time it must still find the correct activation record of the enclosing procedure. This is why access links or displays are needed.

Manipulating Access Links

CaseMeaningAction
np > nqCalled procedure is nested deeperAccess link points to caller's AR
np < nqCalled procedure is shallowerFollow caller's access-link chain for nq - np + 1 hops
np == nqBoth at same nesting levelCalled procedure gets the same access link as caller

Access Links for Procedure Parameters

If a procedure is passed as a parameter, its lexical context must also be passed. So the caller sends the procedure name together with the proper access link.

Variable-Length Data on Stack

Some local data sizes are known only at run time. In that case, the fixed-size part stays in the activation record, while variable-length objects are managed above it on the stack using pointers plus top and top_sp.

Maintaining the Display

When a procedure at nesting depth i starts, store the old d[i] in its AR and update d[i] to point to the current AR. On return, restore the previous value.
